## WP2. Bulk import and never-crawl list (app + admin UI) — 2026-11-17

**What was built**

- `POST /api/admin/crawl-sources/import` (`crawler:manage`, CSRF-checked, 503 `crawler_disabled` while `ENABLE_CRAWLER` is off): up to 1000 entries per request, bare hosts or full URLs (the host is extracted, then validated exactly like a single add). One result per entry — `created`, `exists` (already a source, or a repeat within the request), `blocked` (built-in never-crawl list or a `CrawlBlockedHost` row, including parent domains), `invalid` — so duplicates and blocked hosts are reported, never errors. Omitted `pageBudget`/`delayMs` default to the WP1 env knobs (`CRAWLER_REPORTED_PAGE_BUDGET` / `CRAWLER_DEFAULT_DELAY_MS`, 2000/1500); `enabled` defaults to false, like the single add.
- `importCrawlSources` (`asmita/src/lib/crawl-sources.ts`): a fixed handful of queries whatever the list size — one read of existing sources, one read of blocked rows over every host and every parent, one bulk insert with ON CONFLICT DO NOTHING (a concurrent import of the same host cannot error or double-create; on the Prisma path one read settles the created rows and their ids) — so 1000 hosts import within the Worker's per-request subrequest limits. Built-in never-crawl hosts are filtered before any query.
- `writeAuditLogs` (`asmita/src/lib/audit.ts`): a batched audit writer — one LOCK, one previous-hash lookup, one insert of all rows, in one transaction, with the same hash chain and row shape as one-by-one writes. `writeAuditLog` now delegates to it with a single event; behaviour is unchanged and no existing test needed to change. Each created source gets one `ADMIN_ACTION` entry, action `crawl_source_imported`, like a single add.
- `GET/POST/DELETE /api/admin/crawl-blocked-hosts` (`crawler:manage`): list, add (host plus reason; the host is validated like a source host), remove by id. Reads work with the crawler off, changes return 503. Every change is audited (`crawl_blocked_host_added` / `crawl_blocked_host_removed`). New module `asmita/src/lib/crawl-blocked-hosts.ts` with memory, Kysely and Prisma paths; no schema change (`CrawlBlockedHost` came with WP1's migration, so no new migration).

## WP3. App-backed frontier (app + crawler) — 2026-11-17

**Status: complete. All checks passed** (`check.sh`, both packages, Node 22).

**What was built**

- App side: new `CrawlPage` table (additive migration `20261117010000_crawl_page_frontier/`): one row per page URL per source — `urlEncrypted` (encryptField) with `urlDigest` unique per source, `depth`, `kind` (page/sitemap/feed, for WP4), `etag`/`lastModified`, `status` (PENDING/FETCHED/NOT_MODIFIED/GONE/BLOCKED/ERROR/DEAD), `claimedUntil`, `lastFetchedAt`, `nextDueAt`, `failCount`. New module `asmita/src/lib/crawl-pages.ts` with memory, Kysely (Worker) and Prisma paths, aligned as required; memory store extended (`crawl-store.ts`).
- `POST /api/crawler/frontier/claim` (strict body, 256 KiB, rate-limited, 503 while `ENABLE_CRAWLER` is off): due rows of one source, selected `FOR UPDATE SKIP LOCKED` on both database paths (Kysely query builder; `$queryRaw` on Prisma) and marked claimed for 30 minutes, so two crawler instances never get the same URL. A source's first claim creates its seed row (`https://<domain>/`). A claim never crosses the source's remaining budget for the UTC day (pages with `lastFetchedAt` today), so a source stops handing out URLs for the day once `pageBudget` pages were fetched. Unknown or disabled sources claim empty, never an error. Validators are returned only when present (optional, not nullable).
- `POST /api/crawler/frontier/report`: per-page strict validation (a malformed entry is skipped without losing the others), scheduling per the spec — first visit as soon as possible; after `fetched` revisit in 24 h; after `not_modified` double the previous interval up to 14 days; after `error` back off 1 h / 6 h / 24 h and dead after 5 failures; `gone` dead — plus `blocked` rechecked after 24 h (the spec gives it no schedule). New in-scope links are stored at the reporting page's depth + 1, deduplicated per source on a keyed digest with the crawler's tracking-param rule (the URL as reported is kept, as findings do), and the in-scope check the crawler does is repeated by the app on every link (host equals the source domain or is a subdomain; credentials, non-default ports and non-http(s) refused, exactly the findings rules). Visited pages move `CrawlSource.pagesCrawled`/`lastCrawledAt`. `accepted` counts the page rows the report moved; DEAD/GONE rows are never resurrected by a late or retried report.
- Retention: `purgeExpiredCrawlPages` (url-retention.ts) runs with the hourly cron alongside the findings purge. Frontier rows follow the same 30 days; a row is operational state, not a record, so it is deleted, not blanked — except rows still due for crawling, which keep their pending work.
- Crawler side: the in-memory frontier (queue, seen set, queuePeak/seenPeak/linksNotQueued) is removed. `src/crawler.ts` claims batches (`FRONTIER_CLAIM_LIMIT`, new config knob, default 50, 1..200), fetches each page with `If-None-Match`/`If-Modified-Since` when the app has validators, maps outcomes (304 → `not_modified`, 404/410 → `gone`, robots or 401/403 → `blocked`, anything else → `error`) and reports results in body-bounded chunks under the server's 256 KiB limit; the report never carries more links per page than the contract's 500 even if `MAX_LINKS_PER_PAGE` is configured higher. The in-scope check stays in the crawler (claimed URL, every redirect hop, post-fetch belt-and-braces). 304 handling, extra request headers and response validators (`etag`, `lastModified`) were added to `src/net/safe-fetch.ts` — the only fetch path, unchanged in every other respect. A page the run was stopped on mid-way is not reported, so it is redone whole after the claim window: a killed run loses at most its claimed batch. New summary fields: `pagesNotModified`, `batchPeak` (the crawler's whole frontier memory is one batch plus its report). Claim/report failures count their error codes; 503/401 stop the run like the other API calls, and a failed report only breaks the source's loop (the claimed pages recover on their own).
- `CrawlDeps.seedUrl` and `runMain`'s `seedUrl` option are gone: seeds are the app's now. The test mock gained a faithful frontier (same rules, written independently) with a fixture `seedUrl`.
- Docs: `crawler/README.md` (run diagram, bounded-frontier row, the two routes, `FRONTIER_CLAIM_LIMIT`, run summary), the runbook (section 2 frontier, env table, go-live migration list), ADR 006 dated note. `crawler/.env.example` gained `FRONTIER_CLAIM_LIMIT`.

**Deviations from the spec, with reasons**

- `blocked` (robots.txt disallow, or a 401/403 answer) is rechecked after 24 h: the spec gives `gone`, `error` and `not_modified` schedules but none for `blocked`. Robots blocks are usually long-lived but can change, so a bounded daily recheck was chosen over killing the page.
- Every `fetched` page is scheduled 24 h ahead, not only fetched pages with new links (the spec names "after `fetched` with new links"); nothing in the contract distinguishes a fetched page without links, and a 24 h revisit is the defined baseline the `not_modified` doubling starts from.
- The daily budget is enforced at claim time as "pages with a `lastFetchedAt` within the UTC day < `pageBudget`", and a claim is also capped at the remaining budget; `error`/`blocked` pages do not count (they were not fetched). This is the reading of "stops handing out new URLs for the day once `pageBudget` pages were fetched that day" that cannot exceed the budget even when runs are killed mid-batch.
- The 30-day purge deletes `CrawlPage` rows instead of blanking them like findings: a frontier row without its URL can never be crawled again, and unlike a finding it is not a record of anything. Rows still due (not DEAD/GONE and past their `nextDueAt`) are kept, as the spec requires.
- A page the crawler is stopped on mid-way is not reported, so it is redone whole after the claim window — the strictest reading of "a killed run loses at most its claimed batch" (its already-hashed findings still go out; the server dedups them on the redo).
- Claim and report are not audited: they are per-page service traffic (orders of magnitude more rows than findings), they carry no admin action and no case link, and the audit log's hash chain would grow by one entry per page crawled. Source changes, findings and reveals stay audited as before.
- A report the server applied but whose answer was lost is re-applied on retry: schedules only move forward, links are deduplicated by digest, so the retry is safe; `pagesCrawled` may count such a page twice. Documented in `crawl-pages.ts`.
- The report caps a page's links at the contract's 500 even when `MAX_LINKS_PER_PAGE` is configured higher (the server would refuse the whole report entry otherwise).
- The mock's frontier seeds fixture sources with `http://<host>:<port>/` (production seeds `https://<domain>/` per spec); the mock also does not apply the app's non-default-port refusal to reported links, because the whole fixture site lives on a port — the port rule itself is covered by the app-side tests.

## WP4. Deep coverage of a site (crawler) — 2026-11-17

**Status: complete. All checks passed** (`check.sh`, both packages, Node 22).

**What was built**

- Sitemaps, end to end on the WP3 frontier: a source's robots.txt `Sitemap:` lines (up to 50, parsed independently of robots-parser) ride on the source's first frontier report as `kind: "sitemap"` links; sitemap indexes and urlsets are `CrawlPage` rows claimed, fetched and scheduled exactly like page rows — there is no second fetch path, and they cost `pageBudget` like any page. A `.gz` body (sitemap.xml.gz served without Content-Encoding) is inflated in memory under the same `MAX_HTML_BYTES` cap. The document kind is sniffed from the root element (`<urlset>`, `<sitemapindex>`, `<rss>`, `<feed>`), never from the URL or the Content-Type, which sites routinely get wrong.
- New `crawler/src/crawl/xml-docs.ts`: a bounded event scanner (no DOM, no new dependency, no temp file) with entity and CDATA handling; the parsers stop at `MAX_SITEMAP_URLS` taken addresses — page `<loc>`, child-sitemap `<loc>`, `<image:loc>` and feed entries all count against it — and at a hard markup-event cap, reporting truncation. Image sitemap `<image:loc>` entries are hashed during the sitemap's own fetch, attributed to their page (the `<loc>`), which must be in scope and not obvious non-content like any page; the normal image caps, budgets and off-scope-host rules apply unchanged.
- RSS and Atom feeds linked from pages (`<link rel="alternate">` with an rss/atom type, and anchors to `.rss`/`.atom`) are reported as `kind: "feed"` rows; their entries become page rows. RSS `<item><link>` text and Atom `rel="alternate"` (else the first rel-less link) are taken; channel-level links and `rel="self"` are not.
- Pagination: `rel="next"` anchors, `<link rel="next">` in the head, and anchors whose text or class marks next/older/page-N are collected into their own bounded bucket and reported first, so a link flood cannot push them past the per-page cap. Pagination-marked links skip the query-variant cap.
- More image candidates (`crawl/extract.ts`): CSS `background-image` in inline styles (every `url()` of background/background-image declarations), `<video poster>`, `<link rel="image_src">`, JSON-LD `image`/`images` (string, array or object with `url`/`contentUrl`; `@graph`-walked with depth and per-block size caps, malformed or oversized blocks counted, never fatal), `<noscript>` fallbacks (bounded re-parse when the parser kept the content as raw text), and the full-size target of a thumbnail link: `<a href=*.jpg><img></a>` now takes the href and suppresses the wrapped thumbnail (its src is a thumbnail of the same picture).
- Trap skipping: login, cart, search-result and calendar URLs are never reported or fetched, whatever markup marks them (exact path segments incl. `wp-login.php`, date-shaped paths `/YYYY/MM…` and `/YYYY-MM-DD`, date query keys, WordPress `?m=YYYYMM`, `?q=`/`?s=`/keyword search keys, `add-to-cart`) — a rel="next" link into an infinite calendar is skipped like any other calendar link. New `crawl/traps.ts` also adds a per-source `QueryVariantGuard`: at most `MAX_QUERY_VARIANTS_PER_PATH` distinct query variants of one path are reported (page-number parameters — `page`, `paged`, `pg`, `start`, `offset`, `from` — and tracking parameters do not count); its state is bounded 16-byte hashes (at most 4096 paths), never a URL.
- Configuration (Zod, fail closed) and docs: `MAX_SITEMAP_URLS` (default 5000) and `MAX_QUERY_VARIANTS_PER_PATH` (default 8) in `src/config.ts`, `.env.example`, `crawler/README.md` (run flow, a new "Deep coverage" guarantee row, config table, run-summary fields, the bounded-state note) and the runbook's frontier section. `run_summary` gains `pagesXml`, `sitemapDocs`, `sitemapUrlsTaken`, `sitemapImages`, `feedsParsed`, `feedEntriesTaken`, `docsTruncated`, `linksSkippedNonContent`, `linksSkippedQueryCap`, `jsonldSkipped`, `noscriptSkipped`. No `asmita/` code changed.

**Deviations from the spec, with reasons**

Both exemptions stay bounded by the same caps as everything else (per-page link cap, depth, budgets).
- Image sitemap entries are hashed at the sitemap's own fetch, attributed to their `<loc>` page, rather than waiting for that page's row to be claimed: the sitemap row is the in-scope fetched page, the image is a candidate extracted from it, and attributing the finding to its real page (in scope, else the image is skipped) is what "image candidates for their page" requires. The usual dedup means the same image is never hashed twice if the page later lists it too.
- "`<a href=*.jpg><img></a>` takes the href" is implemented as: the href becomes the image candidate and the wrapped `<img>` is suppressed. Taking both would hash a thumbnail and its full-size copy of the same picture, doubling fetches for no finding.
- The non-content URL patterns are deliberately narrow — exact path segments, date-shaped paths, specific query keys — so nothing ambiguous is skipped; "obvious non-content" only. `?p=` (WordPress post ids) and bare numeric id parameters are content addresses, not traps, and are kept.
- Robots.txt `Sitemap:` discovery is attached to a source's first *reported page entry* of the run (whatever its status) rather than fetched outside the frontier: keeping sitemap fetches inside the claim/report path preserves every WP3 guarantee (two crawlers never fetch the same URL, a killed run loses only its batch, budgets count it), at the cost of sitemaps being discovered a claim later than a direct fetch would manage.

**Status: complete. All checks passed** (`check.sh`, both packages, Node 22).

**What was built**

- Rendering rule, exactly as specified: a source with `render = BROWSER` has every HTML page rendered; an `AUTO` page is rendered only when its HTML carries a script tag and the static extractor finds no image candidates; `http` (the default) never launches a browser, and a run with no browser sources never spawns the worker (it is started lazily on the first render).

One page at a time, always: the parent-side renderer (`src/browser/browser-renderer.ts`) serialises renders, so the spec's "one page at a time per source" holds a fortiori across sources. The worker gets a scrubbed environment (TMPDIR/HOME = the memory temp dir, `PLAYWRIGHT_BROWSERS_PATH` only — never a key, config or fingerprint), runs under Node's permission model (reads: its own bundle, the node_modules listing and `playwright-core`, the browser directory, read-only system metadata; writes: only the memory temp dir; child process allowed for Chromium; no addons, no worker threads) and has stdout/stderr discarded like the decoder's. The IPC protocol (`src/browser/protocol.ts`) is validated strictly on both sides and any unexpected shape, field or id kills and replaces the worker — the decoder rule.
- All browser traffic goes through an in-process forward proxy (`src/net/browser-proxy.ts`): a SOCKS5 server, because with a SOCKS proxy Chromium hands the proxy the hostname (remote DNS), so the proxy sees every destination before it is contacted and no HTTP absolute-URI parsing is needed. It applies the same `NetPolicy` object safe-fetch uses: the port must be allowed (checked for both schemes, since SOCKS carries none), the hostname is resolved through the policy's resolver and refused when ANY address is blocked, and the dial goes to the validated address — no rebinding window. A literal destination (Chromium sends literal IPs as domain-type strings) is checked directly against the blocklist. Chromium is launched with `--proxy-bypass-list=<-loopback>` so even loopback destinations go through the proxy (and are then refused by the production policy). Per render the parent sets a byte account: all tunnels summed must stay under `BROWSER_MAX_PAGE_BYTES` or the proxy destroys them, the render aborts and the page reports `error`.
- Nothing on disk: no persistent profile (a fresh context per render; Playwright's throwaway profile lives under the worker's TMPDIR, which the parent points at `BROWSER_TMP_DIR`, a tmpfs — `/dev/shm` in the container, `--shm-size=1g` documented), disk cache disabled, downloads refused, service workers blocked. Image bytes are taken from intercepted responses in memory, capped per image in the worker and re-checked by the parent, and go through the same size caps and the same decoder child process as every other image (the shared decode→match→report tail in `crawler.ts` is one function for both paths). The no-disk-write test now covers the browser path as far as Node can observe it (below).
- Honest User-Agent: Chromium's own default with `CRAWLER_USER_AGENT` appended, read once from a blank page (no network). No stealth plugins, no fingerprint spoofing. robots.txt is still honoured: every request the page wants to make — documents and subresources — is intercepted in the worker, counted against a per-page request cap, kept inside the source's scope for navigation requests, and waits for the parent's verdict (the parent owns the robots cache; a URL the network policy itself would refuse is denied without a robots fetch). The page itself is also robots/delay-checked before the render (the HTTP pre-fetch's beforeHop).
- Time and resource caps per page: `BROWSER_PAGE_TIMEOUT_MS` (30 s deadline, then abort, then SIGKILL), `BROWSER_SCROLLS` bounded scroll steps to trigger lazy loading, `BROWSER_MAX_REQUESTS_PER_PAGE` (excess aborted before the network), `BROWSER_MAX_PAGE_BYTES` at the proxy, and the usual image caps. All through `src/config.ts` (Zod, fail closed) and `.env.example`.
- Crawler flow: every page still does the WP3 HTTP pre-fetch (conditional GET, 304 → `not_modified` and no render, 404/410 → `gone`, robots/401/403 → `blocked`, non-HTML → no render), so a rendered page is fetched twice — once by safe-fetch, once by Chromium; the pre-fetch's redirect scope, robots and delay checks all still run. A successful render reports the page `fetched` with links extracted from the rendered DOM (in scope, depth-gated, capped) and no validators (see deviations). Images are the intercepted responses processed as they arrive: scope/robots/off-site-host caps/dedup/budget apply as in the HTTP path, findings carry the page as claimed and the image as the browser fetched it. A BROWSER page whose render fails reports `error` (the app backs off); an AUTO page falls back to its static result.
- `GET /api/crawler/sources` fields `origin`/`hops`/`render` (in the app's contract since WP1) are now required in the crawler's `SourcesSchema` and read; 12 test/support Source literals gained the three fields.
- New error codes (`browser_launch_failed`, `browser_failed`, `browser_aborted`, `browser_timeout`, `browser_protocol`), new `summary.browser` counters (renders, failed, images), new run-summary fields documented.

**Deviations from the spec, with reasons**

- The forward proxy is SOCKS5, not an HTTP CONNECT proxy: with SOCKS5 Chromium sends the hostname (remote DNS), so the proxy decides every destination and no absolute-form HTTP request rewriting is needed; the port rule is checked for both schemes since the SOCKS handshake carries no scheme. The spec asked for "a forward proxy that applies the same address policy" — SOCKS5 is that, with the same resolve/check/dial guarantee.
- "A script that requests a private address is refused by the proxy": with the robots verdict running before every request, such a request is refused one layer earlier — the verdict consults the same policy (a literal blocked address is denied without even a robots fetch), so the proxy never sees it. The page observes both refusals (the integration test's marker link appears only when both fetches fail), the proxy's own refusal is proven directly by the unit test driving raw sockets at it, and no-direct-egress is proven by the fixture hostnames existing only in the test policy's DNS (a successful render means the proxy resolved them). The outcome the spec wants — a private address requested by a rendered page is never fetched — is what is tested.
- Every request, not only documents, waits for the robots verdict. Parity with the HTTP path, where every image fetch is robots-checked before the network; a hostile page referencing many unknown hosts causes at most one robots.txt fetch per origin, bounded by the per-page request cap.
- Rendered pages report no ETag/Last-Modified, so a browser page is never 304-suppressed: the browser's GET cannot be conditional, and validators from the pre-fetch would let a later 304 on unchanged HTML skip the render — but a page whose HTML is unchanged may still render differently. Browser pages revisit at the 24 h base interval. (The pre-fetch itself still stores validators for AUTO pages that fall back to the static path.)
- BROWSER sources fetch every page twice (safe-fetch pre-fetch + the browser's own GET). Kept because the pre-fetch gives WP3 its conditional-GET, gone/blocked and non-HTML handling for free, and it is one extra document request per rendered page; the alternative — sending validators into a browser navigation — would make a 304 a navigation error Chromium cannot classify.
- In browser mode, image candidates are the intercepted responses only; static candidates from the pre-fetched HTML are not re-fetched separately. The spec says image bytes are taken from intercepted responses, and re-fetching DOM candidates the browser chose not to load would double requests for images already downloaded.
- Rule 4's "no proxies" is read as no third-party or anonymising proxies; the spec's own WP7 mandates this in-process policy proxy, which adds no anonymity (same source IP, one honest User-Agent, no rotation).
- The runtime image left distroless. Chromium needs its shared-library set, and copying dlopen-loaded libraries into distroless without a package manager is not maintainable; `node:22-bookworm-slim` with playwright-core's pinned install keeps the read-only, non-root posture. `--no-sandbox` is passed to Chromium (no setuid helper on a read-only root filesystem) and documented with the decoder's deployment-hardening items; the browser worker runs as the job's user.
- `BROWSER_TMP_DIR` defaults to `/dev/shm` and browser sources fail closed where it does not exist (macOS dev machines); the container flags are documented in the README and runbook.
