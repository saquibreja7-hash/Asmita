# Review console progress

One entry per work package of `review-console-spec.md`, appended by the lane that built it.

### WP140 done

Review jobs: the data model, the lease claim and the decisions, with no UI. Built by Hermes on win-desktop, 22 November 2026.

**What was built**

- **Data model** (migration `20261122100000_review_jobs`, additive only, RLS on every table like `20261119150000_partner_feed`): `ReviewQueue`, `ReviewJob`, `ReviewDecision`, `ReviewJobClaim`, `ReviewSkip`, plus the `ReviewSubjectKind`, `ReviewJobStatus` and `ReviewEnqueueSource` enums. One open job per subject is a partial unique index (`subjectKind, subjectId WHERE status = 'PENDING'`), written as raw SQL in the migration because Prisma cannot express it; a second enqueue merges into the open job. The six system queues are seeded create-only by `prisma/seed.ts` and on demand by `ensureSystemQueues()` (`src/lib/review-queue-seeds.ts` is the one source for both).
- **Library** `src/lib/review-jobs.ts`, on all three backends (memory, Kysely on the Worker, Prisma): `syncReviewJobs` (the source tables stay authoritative; opens, closes as `resolved_elsewhere` with a system `close_stale` decision, and moves jobs between queues), `claimNextJob` (one raw `UPDATE ... FOR UPDATE SKIP LOCKED` statement on Postgres, exactly the spec's, plus a `ReviewJobClaim` row; the memory backend has the same semantics single-threaded), `extendClaim`, `skipJob` (30 minutes, this reviewer only), `releaseJob`, `decideJob` (server-side reason enforcement, idempotent retry, one transaction for the decision, the job closure and the claim closure), `moveJob` (decision `move`; moving out of minor-hold refused), `queueSummaries`, and the throttled `maybeSyncReviewJobs` (once per 30 s per isolate). The sync runs from the existing maintenance cron, which now also reports `{enqueued, closed, moved}`.
- **Adapters** `src/lib/review-adapters.ts`: a typed map per subject kind that transcribes today's routes — the same permission, the same existing library function, the same follow-ups (the fingerprint reject voids signatures and the fingerprint approve sends the signed hash advisory, both exactly as `src/app/api/admin/hashes/[hashId]/*` does). `src/lib/lab/lab-review-adapter.ts` registers the Lab's adapter from the Lab side; queue code never names a lab function. Decisions offered: links approve/reject, fingerprints approve/reject, findings approve/dismiss/label_possible_minor, partner applications contacted/approve/decline, lab reports send_email/send_web_form.
- **Minor check first**: a finding under a "Possible minor" label goes to the protected `minor-hold` queue whatever else is true (an open job elsewhere is moved and its lease released), `minor-hold` is SUPER_ADMIN-only in `queueSummaries`/claim/decide/move and every job route, and no decision or move can act on a job inside it; the console's `label_possible_minor` closes the adult-queue job and reopens the subject in minor-hold in one transaction. When the label is cleared through the existing second-admin flow, the sync moves the subject back to its kind's queue.
- **API**: `POST /api/admin/review/[queueKey]/claim`, `POST /api/admin/review/jobs/[jobId]/{extend,skip,release,decide,move}`, `GET /api/admin/review/summary` — CSRF and admin auth like the other admin routes, Zod bodies, `cases:read` to see the complaint queues, the adapter's permission to decide, `lab:manage` for lab reports, SUPER_ADMIN for `minor-hold`.
- **Entry points** open a job the moment a subject enters review (flagged links in `addUrlsToCase`, fingerprints in `addHashesToCase`, findings in `recordCrawlFindings`, partner applications in `recordPartnerApplication`, lab drafts in `draftLabReport`); every hook is best-effort, and the sync backfills.
- **Memory-path gaps closed** so the console's dev/test backend works: `reviewHashSubmission` and case-ops `reviewSubmittedUrl` gained memory twins (both were database-only), and `listHashReviewQueue` gained a memory branch. The dev hashes page and the flagged single buttons could not work without a database before this.

**What was verified, and how**

- Vitest, 60 new tests in four files: `tests/unit/review-jobs.test.ts` (memory backend: the lease — two reviewers never share a job, an expired lease is handed over, a refresh returns the same job; the reviewer-scoped 30-minute skip; one open job per subject; the sync opening and closing for every kind; minor-hold precedence and the refusal to move out; idempotent decide; `claim_lost`; reason enforcement; queue visibility per role; no address in any job, decision, claim or skip row, and the reason note stored encrypted), `tests/unit/review-adapters.test.ts` (every adapter calls the existing function with today's arguments — spies — and refuses a role without its permission before anything runs; the existing functions' refusals pass through unchanged), `tests/unit/review-jobs-kysely.test.ts` (the Worker path against a recording fake: the one-statement claim with the ReviewSkip subquery and FOR UPDATE SKIP LOCKED, the decide/move/sync transactions behind the PENDING guard), `tests/unit/review-jobs-prisma.test.ts` (the Node path against a mocked client: the same claim statement with its parameters, the decide transaction, the idempotent retry, the create-only queue seeding).
- The full local suite passes: 2366 tests, lint 0 errors, `tsc --noEmit` clean, `prisma validate` and `prisma generate` clean, and `C:\hermes\check.ps1 -Scope asmita` ends with ALL CHECKS PASSED.

**Not verified on this machine**

- No Playwright here: WP140 has no UI and the spec's WP140 test list names no e2e spec, so none was written; the review loop's e2e specs come with WP141.

**Sentences the owner should approve (user-facing behaviour)**

- A reviewer pressing "Start reviewing" gets one item at a time with a 10-minute lease; a refresh keeps it, an expired lease hands it to a colleague, and nobody can decide an item someone else holds.
- A rejection or any other decision from the console records its reason internally, encrypted; it never reaches the survivor, whose link shows the same empty flag reason as today's one-click buttons on the Flagged page.
- Approving a fingerprint from the console sends the survivor's signed hash advisory to the platforms she chose, exactly as the Fingerprints page does today; the console adds no new path, it presses the same button.
- An analyst who suspects a minor can press "Label Possible minor" from the console: the item leaves the adult queue at once, only a SUPER_ADMIN sees it again, and it comes back only through the existing two-person label-clearing flow.

**Decisions made on this lane**

1. `ReviewQueue.subjectKind` is nullable: null means "any kind", which is how `minor-hold` accepts every subject kind. The spec's five `ReviewSubjectKind` values are unchanged.
2. Flagged-link jobs use `isAwaitingReview` (the predicate the review buttons enforce) rather than the Flagged page's broader display predicate, so a job never opens for a link its own button would refuse (a flagged link already removed or rejected).
3. The minor check keys on the finding's "Possible minor" label only: no case carries an under-18 field, because a minor never reaches case creation (the eligibility gate refuses before any row exists). When a case-level minor flag is ever added, it belongs in `queueForSubject`.
4. `ReviewDecision.auditEventId` stays null for now: `writeAuditLog` cannot return the id of the row it wrote. The existing functions' audit events remain the audit record; the field is there for when the audit writer can report ids.
5. Console reasons are internal (WP142's rule, applied from WP140): the flagged-link and fingerprint adapters never pass their note as the row's `flagReason`, because the survivor sees the link one and WP142 forbids sending reasons out.
6. The fingerprint adapter mirrors the existing approve/reject routes completely — including the signature voiding after a rejection and the signed-advisory dispatch after an approval — so console behaviour is identical, not a subset and not a new dispatch path.
7. The Lab adapter's send-by-email uses the chokepoint's own abuse address (the Lab page's prefill rule); an address that is not an email answers `no_abuse_email` and the analyst uses the AI Lab page, where the address is typed.
8. The Lab's adapter registers from the Lab side, and the queue code loads that module lazily — the one sanctioned seam, because registration only from Lab pages would leave lab jobs undecidable in a fresh Worker isolate. The enforced boundary holds: the repo's lint passes with the seam in place, and nothing outside the Lab names a lab function.
9. `skipJob`/`releaseJob`/`extendClaim` require the caller's own lease; `moveJob` does not (a SUPER_ADMIN may move an unclaimed job, e.g. into minor-hold), and any move releases the lease the job had.
10. A first approval that still needs a second analyst records no `ReviewDecision` (`jobId` is unique per decision) and releases the lease; the existing function's own audit entry is the record of the first approval.
11. The lazy sync swallows its own failure with a fixed log code and waits for the next window; the maintenance cron is the reliable run and reports its counts.

Ctrl/Cmd+Enter and Esc stay on when the switch is off: chords cannot be typed by accident, and submitting from the reason field is the point of the chord.

**What was built**

**Decisions made on this lane**

1. The spec seeds "findings reject" reasons under the findings queue's reject-kind decision, which the adapter calls `dismiss`; the seeds carry the adapter's own decision codes so the picker and the server agree.
2. "Other requires a note" is carried by the seeded code `other` (the spec's "Other (explain)"), one rule shared by the panel and `decideJob`; the spec's `ReviewReason` model is unchanged rather than growing a `requiresNote` column.
3. A picked reason is validated on the server against the queue's active reasons (unknown, wrong-decision or deactivated → `invalid_reason`); the spec names the flag enforcement for the server, and a picker whose codes the server ignores would make deactivation meaningless. A note without a code remains a valid reason (WP141 behaviour).
4. Reason changes audit as the existing `ADMIN_ACTION` (entityType ReviewReason, ids and the action only) rather than a new enum value; the spec names `CASE_NOTE_ADDED`/`CASE_NOTE_DELETED` as this WP's only enum additions.
5. The settings page is gated on SUPER_ADMIN, not a new permission — `review:manage` is WP144's, and inventing it early would pre-empt that WP. The nav model cannot express "SUPER_ADMIN only", so the queue list page links the page for owners instead; WP144 gives both the permission and the nav item.
6. Notes refuse anything `containsUrlLikeText` matches (the saved-views helper), the same rule the case URL fields already enforce: a survivor's address never enters a note even encrypted, and the reasoned, logged Reveal stays the only way to see one.
7. The guidance .md files are the editable source; the Worker cannot read repo files at runtime, so a postinstall script embeds them in a generated module (the Kysely-types pattern), and a unit test keeps the two from drifting.

Routing rules. Built by Hermes on win-desktop, 22 November 2026.

**What was built**

- **Data model** (migration `20261122140000_review_routing_rules`, additive only, RLS on every table like every other): `ReviewRoutingRule` (name, subjectKind, sequence, `condition` Json, destinationQueueId, priority, status DRAFT/LIVE/DISABLED, version, createdBy email hash), the append-only `ReviewRoutingRuleVersion` (one row per saved version, unique on ruleId+version), and `ReviewRoutingLog` (jobId, ruleId, ruleVersion, matched, details, unique on jobId+ruleId+ruleVersion so a re-run that changes nothing writes nothing). `ReviewQueue` gains a nullable `archivedAt`; `AuditEventType` gains `REVIEW_RULE_CHANGED`.
- **Conditions** (`src/lib/review-routing.ts`): `{ all: [...] } | { any: [...] }` of `{ field, op, value }` leaves, one level, 1–10 leaves; ops `eq | neq | lt | lte | gt | gte | in | is_empty`. Fields are a fixed, typed allowlist owned by each kind's adapter (`routingFields`/`routingFacts` on the adapter, so the Lab registers its own from the Lab side): FLAGGED_LINK platformTier/platformKey/urlSource/flagReason/caseMode/ageHours, FINGERPRINT algorithm/quality/caseMode/ageHours, FINDING method/distance/quality/consentScope/sourceKind/labels/ageHours, PARTNER_APPLICATION platformTier/ageHours, LAB_REPORT chokepointKind/ageHours. Unknown fields, wrong operators for the type, out-of-list enum values, empty `in` lists and nesting are refused on save; existing columns only, never survivor free text, never an address.
- **Evaluation**: the minor check runs before anything (a possible minor never reaches the rules), then LIVE rules of the kind in sequence order; the first valid match sets the queue and the priority, no match uses the kind's default queue. A DRAFT that matches before the winner is logged as `would_have_matched` with no effect (shadow mode); a rule whose destination queue stopped being valid is skipped and logged `invalid_destination`. DISABLED rules never run. Evaluation happens in `enqueueForReview` (a routed job is created with `enqueueSource: RULE`) and in `syncReviewJobs` (open jobs move, in-place priority patches don't disturb a holder, and a disabled rule moves items back on the next pass). The sync loads each kind's rules once per pass; a kind with no rules loads no facts at all.
- **What a rule can never do** is enforced in code and pinned by tests: no call to any decision function on the evaluation path, no audit event beyond `REVIEW_RULE_CHANGED`/`ADMIN_ACTION`, the destination must be a same-kind, non-protected, non-archived queue on save and is re-checked at evaluation and on every switch to LIVE, and nothing can route into or out of `minor-hold`.
- **The job screen** now says why an item is where it is: "Routed here by rule X (version N)" or "Default queue", plus a muted line naming draft rules that would have matched.
- **APIs** (all CSRF, admin-auth, Zod, rate-limited, `review:manage` re-checked in the library): `POST /api/admin/review/rules` (create as DRAFT v1), `POST .../rules/[ruleId]` (save), `.../status`, `.../move` (up/down), `POST .../rules/test` (the dry-run Test panel: every rule of a kind against an open job id or hand-entered values, per condition, with the queue that would be chosen — nothing routed, nothing logged), `POST /api/admin/review/queues` (create custom queue), `POST .../queues/[queueId]` (rename), `.../archive`.
- **UI** `/admin/review/rules` (`review:manage`, the new SUPER_ADMIN-only permission, one WP earlier than WP144's own list because the spec names it here): per-kind sections with rule cards in sequence order, the default queue pinned last and not editable, an inline structured builder (field/operator/value controls typed per field), Move up/Move down buttons, a status switch, a version history with who and when (handles, never emails), and the Test panel; plus the queues admin on the same page (add/rename/archive custom queues; system queues and `minor-hold` refused). The nav gains "Routing rules" under Review, and the queue list links it for owners.
- **Queues admin rules**: keys derive from the name and never change; only custom queues are editable; only empty custom queues no rule points at can be archived (a rule of any status blocks it, so a live rule never loses its destination quietly); `moveJob` into an archived queue is refused; archived queues are hidden from `queueSummaries` and can never be a destination.

**Sentences the owner should approve (user-facing behaviour)**

- A routing rule only picks which queue an item waits in and how urgent it is; it never approves, rejects, sends or labels anything, and the reviewer still presses the same buttons as today.
- Rules are built from fixed fields only — platform tier, age, quality, labels and the like — never an address, never survivor text; anything a rule is not allowed to read is not offered.
- A new rule is a draft: it logs "would have matched" without touching anything until the owner switches it Live, and every save, switch and reorder is versioned and audited with who and when.
- The review screen now says why an item is where it is: "Routed here by rule X (version N)" or "Default queue".
- Only the owner (SUPER_ADMIN) can see or change routing rules and custom queues; system queues cannot be archived, the protected Possible minor queue cannot be edited, and nothing a rule does can move an item into or out of it.

**Decisions made on this lane**

1. `platformKey` is the platform directory's stable id slug (e.g. `youtube`): there is no `key` column, and the seeded `Platform.id` is that key everywhere. On the memory backend it is resolved by domain, because the dev store keeps no platformId on a URL row — the same resolution the row's own platformName uses.
2. PARTNER_APPLICATION `platformTier` is the tier of the platform directory entry matching the applicant's website domain, through the app's own existing matcher (`findPlatformByDomain`, the same one `parseSubmittedUrl` uses for a submitted host); nothing is fetched, and an unknown domain reads as empty. No application row carries a tier of its own.
3. FINDING `sourceKind` is `CrawlSource.origin` (ADMIN/REPORTED/DISCOVERED/PARTNER), not `CrawlSource.kind`: `kind` has the single value SITE and could never route anything, while origin is the signal the console already shows.
4. Set-valued fields (flag reasons, labels) match per code: `eq` contains it, `neq` does not, `in` any-of, `is_empty` none; a missing value never satisfies a comparison, not even `neq`.
5. Evaluation stops at the first LIVE match — later rules are never consulted and never logged, exactly Coop's first-match; a matching DRAFT before the winner is logged as shadow, and the Test panel is the place that evaluates every rule (post-winner matches read "not reached" there).
6. "Log every evaluation" is one deduplicated row per (job, rule, version): the sync evaluates every open job every pass, but a re-run that changes nothing writes nothing; the log is pruned after 90 days by the maintenance cron, and its details carry outcome codes and booleans only — never a field value.
7. A job whose queue a rule chose at creation records `enqueueSource: RULE` (the enum value WP140 left for this WP); a sync-created job without a match stays SYNC, and moves stay MOVED.
8. Queue admin changes (create/rename/archive) audit as the existing `ADMIN_ACTION` with ids only, following WP142's precedent — the spec names `REVIEW_RULE_CHANGED` as this WP's single enum addition, and that event belongs to rule changes alone.
9. Only custom queues are editable; the spec's "rename them" reads as the custom queues it has just introduced, so system queues and `minor-hold` are refused by the library, not just hidden.
10. `review:manage` exists from this WP (SUPER_ADMIN only) because the spec's own WP143 UI line names it; WP144 then applies it to reasons, access and the admins page as its list says.
11. The Lab's routable fields are `chokepointKind` and `ageHours`, registered from the Lab side through the adapter like everything Lab; queue code still never names a lab function.
12. Found and fixed in passing: the WP141 job screen's subject card overflowed at 390px (a `dl` grid with no base column count made every field its own column below 640px). One class added (`grid-cols-1`); the same pass caught the add-rule form's missing `subjectKind`. Both are recorded here because both were found by this WP's own 1280/390 design pass.
