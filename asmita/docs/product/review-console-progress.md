# Review console progress

One entry per work package of `review-console-spec.md`, appended by the lane that built it.

### WP140 done

Review jobs: the data model, the lease claim and the decisions, with no UI. Built by Hermes on win-desktop, 22 November 2026.

**What was built**

- **Data model** (migration `20261122100000_review_jobs`, additive only, RLS on every table like `20261119150000_partner_feed`): `ReviewQueue`, `ReviewJob`, `ReviewDecision`, `ReviewJobClaim`, `ReviewSkip`, plus the `ReviewSubjectKind`, `ReviewJobStatus` and `ReviewEnqueueSource` enums. One open job per subject is a partial unique index (`subjectKind, subjectId WHERE status = 'PENDING'`), written as raw SQL in the migration because Prisma cannot express it; a second enqueue merges into the open job. The six system queues are seeded create-only by `prisma/seed.ts` and on demand by `ensureSystemQueues()` (`src/lib/review-queue-seeds.ts` is the one source for both).
- **Library** `src/lib/review-jobs.ts`, on all three backends (memory, Kysely on the Worker, Prisma): `syncReviewJobs` (the source tables stay authoritative; opens, closes as `resolved_elsewhere` with a system `close_stale` decision, and moves jobs between queues), `claimNextJob` (one raw `UPDATE ... FOR UPDATE SKIP LOCKED` statement on Postgres, exactly the spec's, plus a `ReviewJobClaim` row; the memory backend has the same semantics single-threaded), `extendClaim`, `skipJob` (30 minutes, this reviewer only), `releaseJob`, `decideJob` (server-side reason enforcement, idempotent retry, one transaction for the decision, the job closure and the claim closure), `moveJob` (decision `move`; moving out of minor-hold refused), `queueSummaries`, and the throttled `maybeSyncReviewJobs` (once per 30 s per isolate). The sync runs from the existing maintenance cron, which now also reports `{enqueued, closed, moved}`.
- **Adapters** `src/lib/review-adapters.ts`: a typed map per subject kind that transcribes today's routes — the same permission, the same existing library function, the same follow-ups (the fingerprint reject voids signatures and the fingerprint approve sends the signed hash advisory, both exactly as `src/app/api/admin/hashes/[hashId]/*` does). `src/lib/lab/lab-review-adapter.ts` registers the Lab's adapter from the Lab side; queue code never names a lab function. Decisions offered: links approve/reject, fingerprints approve/reject, findings approve/dismiss/label_possible_minor, partner applications contacted/approve/decline, lab reports send_email/send_web_form.
- **Minor check first**: a finding under a "Possible minor" label goes to the protected `minor-hold` queue whatever else is true (an open job elsewhere is moved and its lease released), `minor-hold` is SUPER_ADMIN-only in `queueSummaries`/claim/decide/move and every job route, and no decision or move can act on a job inside it; the console's `label_possible_minor` closes the adult-queue job and reopens the subject in minor-hold in one transaction. When the label is cleared through the existing second-admin flow, the sync moves the subject back to its kind's queue.
- **API**: `POST /api/admin/review/[queueKey]/claim`, `POST /api/admin/review/jobs/[jobId]/{extend,skip,release,decide,move}`, `GET /api/admin/review/summary` — CSRF and admin auth like the other admin routes, Zod bodies, `cases:read` to see the complaint queues, the adapter's permission to decide, `lab:manage` for lab reports, SUPER_ADMIN for `minor-hold`.
- **Entry points** open a job the moment a subject enters review (flagged links in `addUrlsToCase`, fingerprints in `addHashesToCase`, findings in `recordCrawlFindings`, partner applications in `recordPartnerApplication`, lab drafts in `draftLabReport`); every hook is best-effort, and the sync backfills.
- **Memory-path gaps closed** so the console's dev/test backend works: `reviewHashSubmission` and case-ops `reviewSubmittedUrl` gained memory twins (both were database-only), and `listHashReviewQueue` gained a memory branch. The dev hashes page and the flagged single buttons could not work without a database before this.

**What was verified, and how**

- The full local suite passes: 2366 tests, lint 0 errors, `tsc --noEmit` clean, `prisma validate` and `prisma generate` clean, and `C:\hermes\check.ps1 -Scope asmita` ends with ALL CHECKS PASSED.

**Not verified on this machine**

**Sentences the owner should approve (user-facing behaviour)**

- A reviewer pressing "Start reviewing" gets one item at a time with a 10-minute lease; a refresh keeps it, an expired lease hands it to a colleague, and nobody can decide an item someone else holds.
- A rejection or any other decision from the console records its reason internally, encrypted; it never reaches the survivor, whose link shows the same empty flag reason as today's one-click buttons on the Flagged page.
- Approving a fingerprint from the console sends the survivor's signed hash advisory to the platforms she chose, exactly as the Fingerprints page does today; the console adds no new path, it presses the same button.
- An analyst who suspects a minor can press "Label Possible minor" from the console: the item leaves the adult queue at once, only a SUPER_ADMIN sees it again, and it comes back only through the existing two-person label-clearing flow.

**Decisions made on this lane**

1. `ReviewQueue.subjectKind` is nullable: null means "any kind", which is how `minor-hold` accepts every subject kind. The spec's five `ReviewSubjectKind` values are unchanged.
2. Flagged-link jobs use `isAwaitingReview` (the predicate the review buttons enforce) rather than the Flagged page's broader display predicate, so a job never opens for a link its own button would refuse (a flagged link already removed or rejected).
3. The minor check keys on the finding's "Possible minor" label only: no case carries an under-18 field, because a minor never reaches case creation (the eligibility gate refuses before any row exists). When a case-level minor flag is ever added, it belongs in `queueForSubject`.
4. `ReviewDecision.auditEventId` stays null for now: `writeAuditLog` cannot return the id of the row it wrote. The existing functions' audit events remain the audit record; the field is there for when the audit writer can report ids.
5. Console reasons are internal (WP142's rule, applied from WP140): the flagged-link and fingerprint adapters never pass their note as the row's `flagReason`, because the survivor sees the link one and WP142 forbids sending reasons out.
6. The fingerprint adapter mirrors the existing approve/reject routes completely — including the signature voiding after a rejection and the signed-advisory dispatch after an approval — so console behaviour is identical, not a subset and not a new dispatch path.
7. The Lab adapter's send-by-email uses the chokepoint's own abuse address (the Lab page's prefill rule); an address that is not an email answers `no_abuse_email` and the analyst uses the AI Lab page, where the address is typed.
8. The Lab's adapter registers from the Lab side, and the queue code loads that module lazily — the one sanctioned seam, because registration only from Lab pages would leave lab jobs undecidable in a fresh Worker isolate. The enforced boundary holds: the repo's lint passes with the seam in place, and nothing outside the Lab names a lab function.
9. `skipJob`/`releaseJob`/`extendClaim` require the caller's own lease; `moveJob` does not (a SUPER_ADMIN may move an unclaimed job, e.g. into minor-hold), and any move releases the lease the job had.
10. A first approval that still needs a second analyst records no `ReviewDecision` (`jobId` is unique per decision) and releases the lease; the existing function's own audit entry is the record of the first approval.
11. The lazy sync swallows its own failure with a fixed log code and waits for the next window; the maintenance cron is the reliable run and reports its counts.

### WP141 done

The review loop UI. Built by Hermes on win-desktop, 22 November 2026.

**What was built**

- **Nav and home**: a "Review" group right under "Needs action" links to `/admin/review`; every admin role sees it, because every role can reach at least one queue and the page itself filters the rows. The "Needs action" tiles for the review kinds (Links to review, Found copies to review, Fingerprints to review) now link to `/admin/review` (the case-list views stay reachable from the Cases page; there is no partner-application tile to change). Flagged, Fingerprints and Findings keep their pages and each gains a "Review one by one" button that opens the matching queue.
- **`/admin/review`** (server page plus `QueueList.tsx`): one row per visible queue in `sortOrder` with name, description, pending count, oldest age as text plus colour (under 4h muted, 4-24h `--coral`, over 24h red with "over a day (...)" wording, so colour is never the only signal), "N held by you", a **Start reviewing** button (disabled with the visible reason "Nothing to review" at zero) and a **Preview** link. Counts re-fetch `GET /api/admin/review/summary` every 15 s while the tab is visible.
- **`/admin/review/[queueKey]`**: the lazy sync, then `claimNextJob`, then a redirect to the job screen; nothing to claim shows the caught-up state (drawn check, "You're all caught up", link back to the queues). Because this page writes a lease, prefetching can never trigger it: the route is force-dynamic (dynamic routes are not prefetched by Next), every link to it sets `prefetch={false}`, and a request carrying `next-router-prefetch` is answered with a redirect instead of a claim.
- **`/admin/review/[queueKey]/[jobId]`**, the job screen: left column scrolling (the subject card in the words the kind's own page uses - for a flagged link case reference, platform, masked address, flag reason, status, age; for a fingerprint algorithm, quality, status, digest; for a finding match, quality, consent scope, labels, source, plus the existing reasoned, logged `RevealAddress`; for a partner application the partners page's fields; for a lab report its facts), then context: the case's other open jobs (queue, age), the case timeline (the case page's markup, extracted into a shared `CaseTimeline` component both pages now render), and previous decisions on the case (shown as "You", "System" or "Reviewer xxxx", never an email, never the note). Right column: a sticky 320px `DecisionPanel` - Guidance (the drawer exists; WP142 writes the per-queue guidance, until then it says no written guidance exists), Skip, "N left in this queue", the adapter's decisions as radio cards with 1-9 key hints, an internal reason note (WP142 builds the reason picker), Submit disabled with a tooltip and visible words ("Choose a decision" / "Choose a reason"). After a submit the next job loads automatically; a decision that kept the subject open (first approval awaiting a second analyst, application marked contacted) carries a one-line status banner to the next screen. A heartbeat extends the lease every 4 minutes while visible; a lost claim shows "Someone else has this now" (or "Your hold on this item ended" / "Nobody holds this item yet", per the actual state) with a "Get the next one" button, and the panel stops submitting.
- **`/admin/review/[queueKey]/preview`**: the queue's pending jobs (subject summary, waiting since, age, priority, held by You / Another reviewer / nobody) without claiming anything.
- **Keyboard**: 1-9 choose a decision, `r` focuses the reason, Ctrl/Cmd+Enter submits, `s` skips, `g` opens guidance, `?` opens the shortcuts sheet, Esc closes drawers. Single-key shortcuts are suppressed while typing in an input, textarea, select or contenteditable, and the sheet carries the per-admin off switch, stored in localStorage wrapped in try/catch (the case list's own pattern). Ctrl/Cmd+Enter and Esc stay on when the switch is off: chords cannot be typed by accident, and submitting from the reason field is the point of the chord.
- **Code paths**: no new decision path anywhere - the panel only calls WP140's job routes, and `describeReviewSubject` (the subject card) is read-only, built from the same loaders each kind's page renders (`listFlaggedLinks`, `listHashReviewQueue`, `getCrawlFindingSummary`, `listPartnerApplications`; the Lab's card comes through the registered adapter because nothing outside the Lab may import lab modules). The view loaders live in `src/lib/review-views.ts` on all three backends; `readAuditTrailForEntities` extends `audit.ts` read-only for the case-plus-item timeline; the job screen records a `case_viewed` access-log entry like the case page and the preview panel do.

**Sentences the owner should approve (user-facing behaviour)**

- Pressing "Start reviewing" hands you one item at a time; you hold it for ten minutes, a refresh keeps it, and an expired hold hands it to a colleague.
- The review screen shows each item the way its own console page does - a link as a masked domain with its flag reason, a finding's address still only behind the reasoned, recorded Reveal - and never the full address.
- Your reason is internal: it is stored encrypted, it is never sent to the survivor or a platform, and the link's own flag reason is not touched.
- If someone else takes your item, the screen says "Someone else has this now", nothing you typed is sent, and one button hands you the next one.
- When your queue is empty the screen says "You're all caught up"; the old Flagged, Fingerprints and Findings pages keep working, each with a "Review one by one" button.

**Decisions made on this lane**

1. The "Needs action" tiles link to `/admin/review` (the queue list), not straight into a claim: a home-page tile should not claim an item on your behalf. The spec says "link here", read as the console.
2. The partner-application kind has no Needs-action tile (none exists today), so the "four review kinds" sentence lands on the three tiles that do; nothing was added to the home page.
3. WP141 ships the note, not WP142's reason picker: the panel's reason is a free-text internal note (the server already enforces the queue's reason flags), and the picker with seeded codes arrives with WP142. The Guidance button opens the drawer WP142 will fill; it honestly says no written guidance exists yet, rather than inventing advice.
4. The claim page refuses to claim on a prefetch: force-dynamic plus `prefetch={false}` plus a `next-router-prefetch` guard, so no link can ever take a lease for an admin who only looked at a page.
5. A lost lease is worded by its actual state - "Someone else has this now" when a colleague holds it, "Your hold on this item ended" when it merely expired, "Nobody holds this item yet" when the URL was opened without claiming - while runtime losses (a refused submit or heartbeat) use the spec's sentence.
6. Single-key shortcuts are suppressed while typing, but Ctrl/Cmd+Enter and Esc remain active everywhere, including inside the reason field: a submit chord that dies in the one field reviewers type in would be useless, and WCAG 2.1.4 is satisfied by the switchable single keys.
7. The job screen's timeline reuses the case page's markup through a shared `CaseTimeline` component, fed by the audit events of the case and the item under review (`readAuditTrailForEntities`); loading the case page's full detail loader per job screen would have cost eight-plus queries and worked on no backend without a database.
8. Previous decisions show "You", "System" or "Reviewer xxxx" (four hex of the email hash) - a short handle, never an email, and never the encrypted note, which no view reads back.
9. Found, out of scope, not fixed here: the nav's "Crawler overview" link points at `/admin/crawler`, but no `src/app/admin/crawler` shim exists - the `(admin)/crawler` page claims `/crawler`, so the nav link 404s today (the WP56/WP57 shim pitfall, missed for this one page). One line fixes it; it belongs to its own change.
