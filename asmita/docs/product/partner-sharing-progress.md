## WP30. Partners and their keys (app) — built 19 November 2026

**What was built**

- `PlatformPartner` and `PlatformPartnerKey` in `prisma/schema.prisma`, with the migration `20261119130000_platform_partners` (additive only, RLS on both tables like every other table). A partner is created only by an admin approving a `PlatformPartnerApplication`; its channel email is encrypted at rest; `crawlPermissionRecordedAt/ById/Note` hold the recorded written permission to crawl.
- `src/lib/partner-store.ts`: the in-memory twin for dev/tests without a database, in the style of `crawl-store.ts`.
- `src/lib/partner-auth.ts` (the spec's file): bearer-key auth for the future partner routes. Keys are `ppk_…`, issued by an admin, only sha256-stored, shown once, revocable, with `lastUsedAt`; lookup by hash plus constant-time compare; IP and per-key rate limits; a suspended partner's valid key answers `403 partner_suspended`, every other key problem answers the same `401 unauthorized`. `readPartnerBody` gives WP32's routes the Rule-6 body cap plus strict-Zod parsing. No `ENABLE_*` switch: a partner is gated by the admin's approval and its key, not a deployment flag.
- `src/lib/partner-admin.ts`: application actions (mark contacted, approve, decline), partner domains and channel email, suspend/reactivate, key issue/revoke, "record written permission to crawl" — every action audited (`ADMIN_ACTION`, `partner_*`), memory/Kysely/Prisma paths like the crawl modules.
- Six admin routes under `/api/admin/partners/…`, all `platforms:edit` + CSRF + strict Zod + per-admin rate limit.
- Admin console: the requests list on `/admin/partners` gained actions and a platform-partners table; a partner detail page (`/admin/partners/[partnerId]`) lists and edits domains, suspends/reactivates, issues keys (shown once, with copy-and-dismiss), revokes keys, and records the written permission (date + note).
- Tests (synthetic data only): `tests/unit/partner-auth.test.ts`, `partner-admin.test.ts`, `partner-admin-routes.test.ts`, `partner-admin-kysely.test.ts`, `partner-admin-prisma.test.ts` — 63 tests covering Rules 5 and 6 as WP30 touches them (admin approval gates, keys issued by an admin and shown once, hash-only storage, revocation honoured, suspension stops authentication, one audit entry per action, per-route rate limits, scoped key access, encrypted channel email, no key material or email in audit data).

**Decisions made on my own**

- On approval the application's contact email becomes the partner's channel email (the ciphertext is copied as-is, no decrypt/re-encrypt round trip; in memory it is encrypted), and admins can edit or clear it on the detail page — the spec lists `channelEmail` on the model and WP33 sends notices there, so it must be settable somewhere.
- `crawlPermissionRecordedAt` stores the date the admin enters (the date on the written permission), not the moment of recording; the recording moment is the audit entry. Re-recording overwrites.
- A domain belongs to one partner: a candidate primary or extra domain that another partner already owns (primary or extra) is refused — `domain_in_use` when editing a partner, `partner_exists` when approving an application — so Rule 1's "the reported URLs on that partner's own domains" is never ambiguous. (Review pass, same day: the approve path had checked only primary domains; it now refuses a domain that any partner owns as an extra domain too, before any write, with a test on each backend.)
- `createdFromApplicationId` carries no foreign key, like `AuditLog.actorId`: provenance, not integrity.
- Same-status changes answer `409 no_change`; re-approving or re-declining a terminal application answers `409 invalid_status`.
- Suspending a partner keeps its keys but they stop authenticating until reactivation.
- Follow-up (same day): `prisma/schema.prisma` and the partners console page had been committed with CRLF line endings, against this repository's LF convention (`core.autocrlf=false`, no `.gitattributes`), which made the branch diff show ~900 phantom changes. Both were normalised back to LF with no content change (verified with `git diff --ignore-cr-at-eol`); every other WP30 file was already LF.

## WP31. The survivor agrees to share (app) — built 19 November 2026

**What was built**

- New template `PARTNER_SHARING_CONSENT` in `prisma/template-seeds.ts`, created unreviewed like every template, seeded to `reviewedByLegal: false`; the wording starts from the plain text the spec gives. `prisma/seed.ts` needed no change.
- `src/lib/partner-share-consent.ts`: the consent's state, the draft she reads (template rendered for the case + the hash annex of the approved fingerprints, `templateRef` pinning text and fingerprint ids), agreeing (one live row per case, template id + digest pinned, refused when the text or fingerprints changed since the page loaded), withdrawal, the account-deletion hook, and `listPartnerShareableFingerprints()` — the Rule 2 query (live agreement × fingerprint `APPROVED`/`DISPATCHED`) with the Rule 3 adult check at the query (`User.ageOver18` on both database backends). Memory / Prisma / Kysely paths like the crawl modules; audits carry internal ids and counts only.
- `/api/cases/[caseId]/partner-share` (GET state + draft, POST agree, DELETE withdraw): CSRF, `requireSession({ adultOnly: true })`, case ownership, 10 changes/hour rate limit, strict Zod (`{ agreed: true, templateRef }` — a name, contact or signature field is a 400), template legal gate unless `DEV_SKIP_LEGAL_REVIEW`, withdrawal always works whatever the switches.
- Case page: `PartnerShareConsent` component under the crawl opt-in, same visual style (no stripes), one tick box "Also share my fingerprints with partner platforms", the eligible fingerprints masked (`••••••••`, like the fingerprints section), a withdraw action with a confirm step (three plain sentences), the full agreement in an optional disclosure. Hidden when there is no approved fingerprint and no live agreement; once she has agreed it stays visible so she can always withdraw. 25 `partnerShare.*` strings in `en.json` and `hi.json`, the Hindi machine-translated and listed in `src/i18n/hi-review-status.json`.
- Deletion wiring: a deletion request withdraws the agreement on every case at once (`deactivateUser`); account erasure deletes the rows on all three backends (Kysely, Prisma, memory store), counted as `partnerShareConsents` in `HardDeleteCounts`. A fingerprint rejection needs no hook: sharing follows the fingerprint's own status.
- Tests (synthetic data only): `tests/unit/partner-share-consent.test.ts` (16), `partner-share-route.test.ts` (17), `partner-share-ui.test.ts` (18), the extended `notice-template-seeds.test.ts`, and the three erasure/overlap tests extended for the new model — Rules 2, 3, 4, 6 and 7 as WP31 touches them. **Decisions made on my own**

- The agreement is standing, not a fixed list: a fingerprint approved after she ticked is covered too. WP32's spec lists approval as a feed event that makes a fingerprint shareable, so the recorded `hashSubmissionIds` are the record of what the page listed when she ticked, not a gate; sharing follows the live agreement plus each fingerprint's own approval. A rejected or deleted fingerprint stops being shared by its status alone, without withdrawing her whole agreement.
- Rule 2's "APPROVED" is read as `APPROVED` or `DISPATCHED` (an advisory already went out), the same approved set the crawl pool uses (`src/lib/crawl-pool.ts`).
- No PDF and no agreement-record block: the spec's column list names no document column, and the tick is not a signature. The template id + digest pin the exact text, the ids pin the fingerprints she was shown, and the audit entry records the account and the time.
- Availability: the tick appears only when hash upload is on, a reviewed template exists, and the case has an approved fingerprint. There is no `ENABLE_*` switch for the partner programme (WP30's decision) and no gate on partners existing — nothing is shared until WP32 serves a feed anyway. Withdrawal works with every switch off.
- Once agreed, the section stays visible even if every fingerprint is later rejected (nothing is shared then, but she must still be able to end the agreement before a future fingerprint is approved). The spec's "hidden when there is no approved adult fingerprint" is applied to the offering of the tick box, not the withdrawal.
- Rule 3 "excluded at the query": the database queries join through to `User.ageOver18`. No separate possibly-a-minor flag exists on cases in the schema, and the memory store carries no age at all, so the memory path relies on the `adultOnly` session gate as everywhere else; the adult filter is asserted on both database backends.
- The full agreement in the disclosure includes the hash annex (like the crawl authorisation), so the text she can read is the text the digest pins; the list beside the tick box stays masked.
- Line endings: the editing tools re-materialised five files with CRLF against the repository's LF convention; all were normalised back to LF with no content change (verified with `git diff --ignore-cr-at-eol`), the same follow-up WP30 recorded.

## WP32. The partner feed (app) — built 19 November 2026

**What was built**

- `PartnerFeedEvent` and `PartnerOutcome` in `prisma/schema.prisma` with migration `20261119150000_partner_feed` (additive only, RLS like every table, `seq` from a Postgres sequence, three new enum values including `AuditEventType.PARTNER_OUTCOME_REPORTED`). No foreign keys on the feed's rows: a withdraw for a purged fingerprint or case is exactly the row that must survive (`AuditLog.actorId`'s pattern). The URL a partner reports is stored encrypted with the same equality digest `SubmittedUrl` uses; on account erasure those rows are deleted (the only partner rows that can hold one of her links).
- `src/lib/partner-feed.ts`: the append-only event log. A fingerprint is shareable while its case has a live agreement, the fingerprint is APPROVED/DISPATCHED and the case is an adult case — re-derived, never cached, on every query (Rule 2, Rule 3 at the query on both database backends). `syncPartnerFeedFingerprints` writes an ADD when a shareable fingerprint's latest event is not an ADD and a WITHDRAW when a shared one stops being shareable, so the feed converges on the truth from any mutation order. The page (`getPartnerFeedPage`) re-checks shareability at serve time and holds back any ADD whose fingerprint stopped being shareable, so the hash of a withdrawn, rejected, unconsented or minor fingerprint is never served; the cursor still advances past held-back events so a poller cannot stall. `kind` is "image" (PDQ, 64-hex) or "video" (VPDQ frame list; the schema has no VPDQ rows yet, the payload shape is ready).
- Trigger hooks, each writing its events in the same transaction as the mutation it follows: the WP31 tick and withdrawal (`partner-share-consent.ts`), the admin hash approval and rejection (`hash-submission.ts` — now one `$transaction`), the dev auto-approve in the sign-hash-advisory route, and account erasure (both `eraseUserWith*` functions in `case-ops.ts`, plus the memory sweep in `store.ts`) — erasure also deletes her `PartnerOutcome` rows and both new counts appear in the `CASE_HARD_DELETED` audit entry.
- `GET /api/partner/v1/fingerprints?cursor=&limit=` and `POST /api/partner/v1/outcomes` under WP30's `authenticatePartner` (key hashed and revocable, suspension answered 403, IP and per-key rate limits, `no-store`): the feed serves at most 500 events per page with `nextCursor`; the outcomes route validates with strict Zod (`fingerprintId` must be one Asmita actually shared; `url` must be on the partner's own registered domains — another partner's domain, a stranger's domain or an unregistered subdomain is 403), stores `PartnerOutcome`, audits `PARTNER_OUTCOME_REPORTED` with ids and counts only, and a "removed" outcome that names a reported `SubmittedUrl` updates that link exactly the way the admin notice-reply path does (guarded `status -> REMOVED` plus a `CONTENT_REMOVED` audit entry), on every case that reported the same address.
- The admin case page lists partner-reported outcomes (outcome, partner and domain, when, the note, which fingerprint it names and which reported link it matched — never the address), through `AdminCaseDetail.partnerOutcomes`.
- `docs/product/partner-api.md`: the integration guide for platform engineers (auth, feed polling and deletion on withdraw, PDQ matching at distance <= 31 with a human review requirement, outcome reporting, rate limits and the partner undertakings), linked from a new FAQ entry on `/for-platforms`.
- The owner's HMA addition: `docs/product/partner-hma-adapter/` (not imported by the app) — `asmita_signal_exchange.py`, a `SignalExchangeAPI` implementation for python-threatexchange that pages the feed with the partner key, keys every update by Asmita's fingerprint id, maps `add` to pdq (vpdq for video) and every `withdraw` to a deletion, uses the feed's `seq` as its checkpoint, and carries `LICENSE-THREATEXCHANGE.txt` (the upstream BSD licence, verbatim, with the source URL); `README.md` covers registration for current HMA (Open Media Match: add the class to `exchange_types` in the OMM config, then `POST /c/exchanges` + `flask auth asmita`), the python-threatexchange CLI (TX_MANIFEST extension) and the archived HMA 1.0. Chosen because stock HMA has no plug-in HTTP exchange at all (python-threatexchange ships only six bespoke in-process APIs — sample, local_file, stopncii, ncmec, fb_threatexchange, tat — read from the ThreatExchange source), so a code drop is needed either way and the adapter keeps Asmita's published feed shape untouched.
- Tests (synthetic data only): `tests/unit/partner-feed.test.ts` (13: event vocabulary, the tick/approval/rejection/withdrawal/erasure transitions on the memory store and the transactional hooks on Prisma, the page's serve-time guard and cursor walk on memory and Kysely), `partner-feed-route.test.ts` (7: authentication end to end, cursor/limit validation, pagination, the global feed, rate limit), `partner-outcomes.test.ts` (10: payload rules and body cap, the domain gate including another partner's domain, the removal path with its audits, the suspended partner, the admin listing); the erasure tests (`account-hard-delete`, `crawl-reported-sources-prisma/kysely`) and the hash-review/admin-case tests were extended for the new models. **Text that needs the owner's approval**

- No new survivor-facing strings and no new template (nothing to set `reviewedByLegal` on; the `PARTNER_SHARING_CONSENT` template's legal review is still WP31's open item).

**Decisions made on my own**

- The feed is one global stream, not per partner: the survivor's agreement is with the programme as a whole ("online platforms that have joined Asmita's partner programme"), the feed carries no URLs, and every ACTIVE partner polls the same log with its own key. Rule 1's per-partner clause ("the reported URLs on that partner's own domains") is served by the notice channel (WP33) and by outcome reporting's domain gate, not by the fingerprint feed; per-partner scoping would also let a partner enumerate another partner's case references. On "a partner only ever sees their own data" (Rule 6): partners see exactly what every partner sees — fingerprints they are entitled to — and their own outcome rows are the only ones their key can write or read.
- Serve-time re-check: the spec's feed shape has no way to un-send an ADD already delivered, so an ADD whose fingerprint has stopped being shareable is left out of the page it would have appeared on (the following WITHDRAW is always served). A partner that polls late sees only the withdraw — the withdrawn fingerprint never appears, which is how "Done means" reads it.
- `seq` is a plain Postgres sequence on the event table (gaps allowed, monotonic, `Int` — 2^31 events is decades at this volume); the cursor is "everything after this seq".
- The outcomes route accepts a URL only on the partner's exact registered domains (a subdomain is not the partner's unless registered, since WP30 keeps one domain with one partner and subdomain matching would make ownership ambiguous). Unknown fingerprint ids are 404 (`unknown_fingerprint`); the response is only `{ ok: true }` — never whether Asmita knew the URL, so the route is not a probe oracle.
- Only the `removed` outcome updates a reported link (the way an admin-recorded removal does); `blocked_reupload`, `not_found` and `not_our_content` are recorded for the case page and metrics. When the same address is reported on two cases, both links are updated and the outcome row points at the first.
- The adapter stores Asmita's `fingerprintId` as the exchange update key (like NCMEC's entry ids) so a withdraw can delete a record whose hash this deployment never fetched; vPDQ quality/timestamp are synthesised in the adapter (the feed carries bare frame hashes) and flagged in its README as the thing to change first if vPDQ ever ships.
- `PartnerOutcome.caseId`/`fingerprintId`/`submittedUrlId` are provenance columns without foreign keys (the `AuditLog.actorId` pattern), so an outcome about a purged link or a kept-but-unshared fingerprint still renders on the case page instead of dying on a join.
- The API base URL in the docs and the adapter default is meriasmita.org (Asmita's own site, as used elsewhere in the codebase); every other domain in the new tests, docs and adapter is `example.test`/`.invalid`.

## WP33. Notices and crawler alerts through the partner channel (app) — built 20 November 2026

**What was built**

- `PartnerChannelSend` in `prisma/schema.prisma` with migration `20261120100000_partner_channel` (additive only, RLS like every table): one row per email sent through a partner's channel, its `dedupKey` (the same sha256 key the send carries to Resend) unique, so a retry — on any isolate — sees the earlier send and never emails twice. Plus `PartnerChannelSendKind`, two audit types (`PARTNER_CHANNEL_SENT`, `PARTNER_CHANNEL_FAILED`) and `CrawlSourceOrigin.PARTNER`. Channel sends are deliberately not `Notice` rows: the escalation sweep reads `Notice` rows with `followUpOf: null` and would send follow-ups to the channel address; `HashDispatch` is the precedent for a small dedicated send table.
- `src/lib/partner-channel.ts`: the channel module. `owningPartner` resolves which partner owns a host (the exact registered domain or its subdomain, longest match wins; WP30 keeps one domain with one partner, so never ambiguous). `copyNoticeToPartnerChannel` — the notice copy: the same subject, body and signed PDF as the grievance-contact send, its own sha256 key to Resend, one row, one audit entry with ids only. `alertPartnerChannelOfFinding` — the alert with the case reference, the page URL on the partner's own domain and the fingerprint id, gated on an ACTIVE partner with a channel email and a recorded crawl permission. `partnerCrawlPermissionMissing` — the findings gate. Send failures are audited (`PARTNER_CHANNEL_FAILED`) and never thrown, so a channel problem can never fail the dispatch or the review that triggered it. Memory / Kysely / Prisma paths like every partner module.
- The notice copy is wired into both notice paths: `/api/notices/dispatch` (the email transport and the platform-API transport, and on the already-dispatched dedup path, so a partner onboarded later still gets the copy of a notice that went out before) and the representative-notice dispatch for crawler links (`crawl-notice.ts`). The routes' responses gain a `partnerChannel` field when a partner matched.
- The crawler side: recording the written permission (`recordPartnerCrawlPermission`) and later domain edits under a recorded permission (`updatePlatformPartner`) now create the partner's domains as crawl sources (`src/lib/partner-crawl.ts`): origin `PARTNER`, created disabled — "the usual admin enable" — with the never-crawl and blocked-host rules and unrecordable hosts (e.g. `.test`) skipped, idempotent, one `ADMIN_ACTION` `partner_crawl_source_created` audit entry each, and never allowed to fail the admin action that triggered them. The console's sources page shows the new origin. Findings whose page host belongs to a partner without a recorded permission are refused at ingestion (`partner_permission_missing`, `crawl-findings.ts`, cached per batch), and an analyst's final acceptance of a finding on a partner's domain sends the alert — after the approval is recorded, with the review flow itself unchanged on both backends.
- Admin metrics (`src/lib/partner-metrics.ts`, on the partner detail page): fingerprints in the feed (distinct fingerprints with an ADD event — the same number for every partner under WP32's shared-feed decision, and the page says so), outcomes reported (the partner's `PartnerOutcome` rows), and the median time from a fingerprint's first ADD to an outcome about it (null when no outcome is measurable). Memory / Kysely / Prisma.
- `docs/product/partner-api.md` gained an "Emails to your channel address" section.
- Tests (synthetic data only), 45 new: `tests/unit/partner-channel.test.ts` (14: ownership matching including longest-match and lookalikes, the copy's gates and dedup, the alert's content rules — never the image address, never a hash value — its gates and dedup, the unrecorded-send and failure paths, the Kysely and Prisma backends), `partner-channel-crawl.test.ts` (4: the ingestion gate, the alert on acceptance with the review unchanged, the alert only after the second of two reviews, approvals that alert no one), `partner-channel-route.test.ts` (3: the copy through the real dispatch route — same signed content to both addresses under different idempotency keys, never a second copy, no change for platforms outside the programme), `partner-crawl-sources.test.ts` (10), `partner-metrics.test.ts` (13), and the representative-notice suite extended by one test. The two Prisma-path crawler fixtures gained only the delegates the new lookups need (`platformPartner`, `case`); no existing assertion changed.

**Decisions made on my own**

- "A notice" covers the two notice paths that carry signed content: the survivor-signed dispatch route and the representative notice for crawler links. Hash advisories are not copied (their fingerprints already reach partners through the WP32 feed, and the codebase has always called them advisories, not notices) and escalation follow-ups are not (the ladder's business, not the channel's). The spec names none of them, so this reading is recorded here.
- The copy and the alert go only to the partner that owns the notice's or finding's host (exact registered domain or its subdomain, longest match first). A partner never receives anything about another platform's or another partner's pages.
- The alert fires at the analyst's final acceptance — including when the approval reused a link the survivor had already reported — and never after the first of two required reviews.
- "Allowed only after crawlPermissionRecordedAt is set" is enforced at ingestion, not only by source creation: a finding on a partner's host is refused even if the host became a crawl source through a survivor's reported link. Until the platform's written permission is recorded, Asmita does not monitor it — and no alert can exist, because no finding is ever recorded.
- The alert re-checks the permission (and ACTIVE, and the channel email) even though the ingestion gate means a partner-domain finding usually implies one: the direct-call paths, a suspended partner and a wiped permission are all gated at the alert itself.
- Channel sends treat Resend's `email_already_sent` as "the email is out — record it now" (`sent: true`, `dedupedByResend: true` in the audit), never as a dispatch failure.
- "Fingerprints delivered" is the shared feed's distinct ADD fingerprints — the same number for every partner, by WP32's global-feed decision, which the admin page now states next to the number.
- The median runs from the fingerprint's first ADD event to the outcome row's creation; outcomes naming an unknown or unshared fingerprint count as reported but contribute no duration.
- Partner domains added after the permission was recorded get their sources at edit time; domains later removed from the partner keep theirs (an admin enabled them by their own act).
- Line endings: the editing tools re-materialised eleven files with CRLF against the repository's LF convention; all were normalised back with no content change (verified with `git diff --ignore-cr-at-eol`), the same follow-up WP30 and WP31 recorded.
