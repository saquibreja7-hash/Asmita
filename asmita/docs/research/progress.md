# Research-grounded tools: progress

One entry per work package of asmita/docs/research/research-tools-spec.md. Each entry starts with "### WPnn done".

### WP116 done

**What was built** — the data foundation for the Indian sextortion classifier, exactly per the WP116 section of the spec:

- **Taxonomy** (`asmita/src/lib/lab/sextortion/taxonomy.ts`, documented in `asmita/docs/lab/sextortion-taxonomy.md`): the 16 message-level labels in the spec's order, multi-label, with label groups (core/supporting/context) and `inferStage()` mapping labels onto the documented ladder (contact → capture → threat → payment → repeat → impersonated authority) to choose advice only, never shown as a verdict.
- **Lexicon** (`lexicon.ts`): per label, Devanagari terms carrying the source ids from `docs/research/2026-11-sources.md` §D where the coverage quotes them, English terms, and romanised Hinglish variants with spelling noise — every romanised entry tagged `derived` (the sources file finds no verbatim romanised threat text). Includes a substring matcher over the two normalised views.
- **Normalisation** (`normalise.ts`): Unicode NFC, zero-width/directional characters stripped, homoglyph folding (Cyrillic, fullwidth, Devanagari digits), Latin lowercasing, ≥3 letter runs collapsed to two, digits-as-letters only inside words and only where unambiguous (0→o, 3→e, 4→a, 5→s), and a fixed ITRANS-like Devanagari romanisation — both script views kept for features.
- **Synthetic generator** (`tools/lab-sextortion/`): deterministic (seed 20261122, byte-identical output, no timestamps), 12 threat families (6,000 rows) and 9 hard-negative families (6,000 rows) split across Devanagari/romanised/mixed/English, optional slots that add labels only when filled, character-level typo/spacing/zero-width noise, and a closed content vocabulary: generated text can only contain tokens from the committed templates and slot pools. Generated data lives in gitignored `data/`.
- **Hand-written evaluation set** (`tools/lab-sextortion/eval/`): 133 threats (≥ 120 required) covering every documented §D pattern and 194 hard negatives (≥ 180 required) — 327 rows (≥ 300), each with labels and script tag, all four scripts in both halves, every taxonomy label present, plus a committed reviewed token snapshot (`vocabulary.json`) as the content-review gate and an `eval/README.md` saying who should replace the examples with human-reviewed ones.

**What was verified and how** — 34 new asmita vitest tests (`tests/unit/lab-sextortion-{taxonomy,lexicon,normalise}.test.ts`) covering the label list, stage inference, source tags (verbatim Devanagari terms carry the right ids, romanised always derived), documented-pattern coverage in ≥2 scripts, all normalisation rules, and matching in each script view. The tool's own suite (33 tests) plus its validator (`npm run check` in `tools/lab-sextortion`: tsc + vitest + full validation) verify determinism (byte-identical), the 6,000+6,000 minimums, script balance, exact family quotas, label coherence (threats never NOT_THREAT), the closed-vocabulary property (noise-free output ⊆ template+slot tokens — the structural no-slurs/no-real-names argument), no 10+-digit runs, no unexpected URLs/emails, MINOR_SIGNAL rows limited to age/school statements, eval counts and script spread, eval texts disjoint from generated texts, and the vocabulary snapshot in sync. Full checks via `powershell … check.ps1 -Scope asmita` end with **ALL CHECKS PASSED** (lint, type-check, 2,340 unit/integration tests).

**Not verified on this machine** — no Playwright run: WP116 defines no page, route or e2e of its own (that is WP117's integration into `/lab/message-check`), so there was nothing to run here and this machine has no Playwright anyway. No model was trained and no classifier metrics exist yet (WP117); the optional MuRIL comparison is explicitly deferred to WP117. Statistical properties of the generated data (label distributions per script) are asserted by the validator, but per-script precision/recall only become measurable when WP117 trains and evaluates.

**User-facing sentences the owner should approve** (none ship in this WP; WP117 will place them on `/lab/message-check`): "Do not pay — paying never ends it."; "The police and CBI never ask for money to delete a video. Report at 1930 or cybercrime.gov.in."; "This is not your fault."; "This check can be wrong. It looks for patterns seen in known blackmail cases."; and the per-label "What we noticed" sentences (e.g. "A threat to send a video to your family").

**Decisions made by the author** (also in the commit message):
1. `inferStage` returns the furthest evidenced rung; it never returns "contact" (a bare approach carries no label, and the page's fixed copy already covers it) and returns null for no labels / only NOT_THREAT / only MINOR_SIGNAL — a stated age alone picks no stage advice because the minor pathway routes first.
2. VICTIM_PLEA evidences the threat rung (a plea presumes a live threat); MORPHING maps to capture (media claimed to exist); DEMAND_THIRD_PARTY maps to capture (a new person to record).
3. "Positive" for counting = any row with a label other than NOT_THREAT (this includes victim pleas and capture-stage openers, which are sextortion-pattern text but never flagged as threats by WP117's core+supporting rule); negatives are NOT_THREAT, optionally with MINOR_SIGNAL.
4. DEMAND_SEXUAL data uses no sexual vocabulary at all — meet-alone, more-media and video-call pressure only (charter: the Lab never generates sexual content); the final dataset and lexicon contain only clinical media words (video, clip, photo, recording, obscene, objectionable).
5. MINOR_SIGNAL rows are exempt from noise: minor routing is rule-based (WP93's `mentionsMinor` runs first), so the age/school statement must stay recognisable.
6. The generator writes no timestamps anywhere, for byte-determinism; the manifest carries seed and version, and WP117's model file will record the seed.
7. `cybercrime.gov.in` was kept out of generator templates (noise can corrupt it, and the URL guard must stay strict) but stays in the hand-written eval negatives, where it is allowed verbatim.
8. The spec's "balanced across scripts" is implemented as each script receiving an equal share of every family (remainders ±2); the duplicate-text rule caps any single text at 100 repeats and requires ≥10% unique rows rather than a blanket percentage — notice families got an invented reference-number slot for variety.
9. The eval set is committed (invented examples are allowed in a public repo) while generated training data is not (rebuilt deterministically); eval/train separation is enforced structurally (id prefixes and text disjointness checked by the validator), and the vocabulary snapshot is the review gate for eval content.
10. No `THIRD_PARTY.md` for this package: no third-party code, weights or data are used; the research datasets named in the sources (HASOC, TRAC, MACD, etc.) are explicitly not used for training or evaluation.
11. No design-skill pass: WP116 has no page layout to design (WP117 does).

### WP117 done

**What was built** — the classifier and its place in the message check, exactly per the WP117 section of the spec:

- **Shared feature extraction** (`asmita/src/lib/lab/sextortion/features.ts`): character 2–5-grams over both normalised script views, word uni/bi-grams over the original-script view, and one feature per matched lexicon term (plus the per-label bit), all hashed into one space. ONE implementation, imported by both the trainer and the Worker-side classifier, so training and inference cannot drift. `lexicon.ts` now also exposes which term matched (`lexiconMatches`), and its taxonomy import became relative so the offline trainer (tsx, no `@/` alias) can load the chain; `tools/lab-sextortion/tsconfig.json` gained `paths` for the same reason (verified in both tsx and tsc).
- **Model and trainer** (`tools/lab-sextortion/src/train.ts`, `npm run train`): one-vs-rest logistic regression per taxonomy label over the hashed features — plain mini-batch gradient descent with L2 decay, seeded deterministic batch order, early stopping on the tuning split's L2-penalised loss, rare positives up-weighted (≤ 5×). Training data: the WP116 generator rebuilt in-process, split deterministically (10,028 train / 1,973 tuning; every 6th row of each family×script run tunes). Thresholds on the tuning split: the mid-point of the separating gap per label (widest margin both sides), else the F1-optimal cut; then the smallest uniform shift δ until the flag rule reaches precision ≥ 0.95 (achieved 1.000 at δ = 0, with 0 false flags on tuning hard negatives; recall 1.000). The eval set is never touched by the trainer. Export: quantized to 1/4096, pruned below |w| < 0.0078, committed as `asmita/src/lib/lab/sextortion/model.json` — 1,938 KiB, under the spec's 2 MB cap — carrying format, trainer version, training date, generator seed and version, hash size and row counts.
- **Inference** (`asmita/src/lib/lab/sextortion/model-format.ts`, `classify.ts`): lazy one-pass decode into typed arrays; `classifySextortion` returns labels and the flag boolean only, so no score can ever leave the isolate. MINOR_SIGNAL is included (the route uses it to send under-18s to support); NOT_THREAT is trained but never surfaced — the page must never tell someone a message is safe. Latency: 4,000 characters classify in ~3 ms median warm (spec budget 20 ms; asserted in tests).
- **Decision logic per spec**: flagged only when THREAT_EXPOSE or CLAIM_HAS_MEDIA is at/above its threshold AND at least one demand/audience/deadline/impersonation label is at/above its threshold — a single keyword is never enough.
- **Stage-chosen advice** (`advice.ts`): advice ids chosen by the WP116 stage inference; "This is not your fault" leads every list; the stage itself is never shown and no sentence names it.
- **Page integration**: `/api/lab/message-check` now runs the WP93 rules AND the classifier, minor routing first (the rules OR the classifier's MINOR_SIGNAL — a school statement the rule set misses, e.g. "main class 10 ki student hoon", is caught by the model). The response carries ids only (matches, labels, flagged, advice). The results card shows one plain sentence per element — the classifier's label sentences first, then the WP93 rule sentences for elements no label covers (`elements.ts`; both lists canonical; crypto/foreign-number rules always shown) — followed by the stage advice and the required line "This check can be wrong. It looks for patterns seen in known blackmail cases." A new "How this check works" section credits the documented Indian patterns (police cyber-crime advisories and news reports 2021–2026), discloses the synthetic training with the honest test-set numbers, and links the bias finding (Sap et al., ACL 2019). Every new string exists in English and Hindi; the Hindi is machine-drafted and recorded in `hi-review-status.json`. No scores, percentages or stage labels appear anywhere; nothing about a message is stored or logged (the route's existing sentinel test now covers the new payload fields).
- **Evaluation** (`asmita/docs/lab/sextortion-eval.md`, `npm run eval-report`): rules-only vs model vs rules+model on the 327 hand-written eval rows. Flag: model precision 100% (39/39), recall 50.6%; rules-only 50.0%/5.2%; rules+model 91.1%/53.2%. No hard negative is flagged by any system (194/194 clean, every family). Per-label and per-script tables expose the bias: no script collapses (flag recall 41–59% per script), but DEMAND_MONEY is the weakest label (17.6% recall overall) and English is the weakest script. MINOR_SIGNAL: 10 of 12 eval rows, zero false fires on adult threats.

**Decisions made by the author** (also in the commit message):
1. The committed model file is Asmita's own artifact, trained on Asmita's own synthetic examples, and the spec explicitly names `src/lib/lab/sextortion/model.json` as the export — rule 3's "model weights are never committed" is read as covering third-party/research weights (MuRIL, GenD), not this file. It is 1,938 KiB, JSON, reviewable in a diff.
2. The "training date" in the model file is a constant in `train.ts` ("2026-11-22"), not the wall clock, so `npm run train` is byte-reproducible; a future retrain must bump TRAINER_VERSION and that date together (the tool's tests pin both to the committed file).
3. Thresholds are chosen per label as the mid-point of the separating gap when the synthetic tuning split separates cleanly (knife-edge thresholds at the top of the positive cluster would not survive paraphrase), with a uniform multiplicative shift toward 1 as the spec's precision-≥ 0.95 lever; on this data the shift is 0 because the max-margin cuts already meet the target.
4. Early stopping watches the tuning loss with the L2 penalty added: plain cross-entropy on this near-separable synthetic split saturates near zero within epochs and would otherwise reward unbounded weight growth (pure phrase memorisation). Two correctness fixes were made under that principle while building, not in response to eval scores: Devanagari combining marks count as letters in word tokenisation (trimming them as punctuation was cutting every Devanagari word at its last matra), and lexicon features are per matched term rather than one bit per label.
5. The eval set was used only as a report, never as a tuning signal, per the spec; the recall numbers it shows (flag recall 50.6%) are the honest cost of the closed synthetic vocabulary, and the eval doc says so on the page and in the tables. The per-script regression floors in the unit tests sit below the measured values, not at them.
6. The rules-only flag baseline is "≥ 2 distinct WP93 rule ids" — the same a-single-keyword-is-never-enough principle the spec applies to the model; the page's own flag remains the spec's core+supporting combination rule, with rule matches shown as elements regardless.
7. A rule whose element a classifier label already covers is not shown a second time (one element, one sentence); crypto and foreign-number rules have no label counterpart and always show. The headline still says "matches patterns" whenever any engine found anything, as the WP93 page did.
8. Stage advice for an unflagged detection is the general list; the stage is never named on the page. NOT_THREAT is trained (the spec says per label) but never surfaced, and MINOR_SIGNAL routes to /minor-support before anything else, including when only the classifier sees it.
9. No aggregate per-day label counters were added: the spec's privacy item permits them ("labels may be counted in aggregate per day") but does not require them, and adding storage to a tool that previously stored nothing would need a schema and a policy decision — left for the owner to ask for.
10. The tool's tsconfig gained `paths` mapping `@/lib/*` into the app tree (no `baseUrl` — TS 6 deprecates it), so tsx and tsc resolve the app's alias imports (e.g. chat-guards under patterns.ts) while running the trainer and the eval report against the real rule code.
