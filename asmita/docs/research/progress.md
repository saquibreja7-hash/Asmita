WP110 — HMA-friendly signal feed, app side (Track A, branch `feat/hma-exchange`, 2026-11-21). The Safety Principles apply in full: this work touches the survivor complaint workflow's partner-sharing path, and every existing gate in `partner-feed.ts` and `partner-share-consent.ts` still holds, with tests.

**What was built**

- `GET /api/partner/v1/signals?checkpoint=<opaque>&page_size=<1..800>` (`asmita/src/app/api/partner/v1/signals/route.ts`, `getPartnerSignalPage` in `asmita/src/lib/partner-feed.ts`): a second read endpoint over the same append-only `PartnerFeedEvent` log, shaped for Meta's Hasher-Matcher-Actioner, without changing `/fingerprints`. Records `{ id, signal_type: "pdq"|"vpdq", hash, deleted, updated_at, tags: ["asmita","ncii","survivor_consented"] }`, ordered strictly by `(createdAt, seq)` of the event, `checkpoint` = base64url JSON `{ "t": <createdAt ms>, "s": <seq> }`. ADD maps to `deleted:false` with the hash; WITHDRAW maps to an explicit tombstone `deleted:true, hash:null`, kept forever (the StopNCII `hashValue`/`hashStatus` bug was studied in the cloned repo and deliberately not copied: deletions here are unambiguous). Same bearer auth, IP limit and `Cache-Control: no-store` as `/fingerprints`, its own per-key bucket `partner-key:<id>:signals` (300/h). A malformed checkpoint is `400 invalid_checkpoint`; an empty or missing one starts from the beginning.
- Serve-time shareability re-check is the same function as `/fingerprints` (`shareableFingerprints`, Rule 2: live consent + APPROVED/DISPATCHED + `User.ageOver18` at the query) — reused, not copied. An ADD that fails the check is skipped while the checkpoint still advances past it, so a caller can never stall. Tested: an ADD whose case consent was withdrawn is never served even when the WITHDRAW event is missing.
- Quality rule: `/signals` never serves a hash whose `HashSubmission.quality` < 50 (HMA does not filter imported hashes by quality, so Asmita filters before publishing — recorded in `docs/product/partner-api.md`). vPDQ: the full frame list is decrypted from `videoFramesEncrypted` at serve time and formatted byte-for-byte as python-threatexchange's vPDQ signal string (`json.dumps` of `"<hash>,<quality>,<timestamp:.3f>"` strings, Python's `", "` list separator included — verified against `json.dumps` output); frames below 50 are dropped, and a video with no frame left serves nothing. `/fingerprints` keeps its contract except that its video `frames` now carry the same full frame list (with the same per-frame filter) instead of the best-frame hash it served before, with a test.
- Performance fix (spec item 2): the Kysely `latestEventTypes` path and the erasure path now query `PartnerFeedEvent` per fingerprint (`.where("fingerprintId", "in", ids)`, served by the new index) instead of scanning the whole table; migration `20261122100000_partner_signals` adds `PartnerFeedEvent (fingerprintId, seq)` and `(createdAt, seq)` indexes, additive only (nothing dropped).
- Key scopes (spec item 3): `PlatformPartnerKey.scopes String[] @default(["feed","outcomes"])` (additive migration; existing rows get both). `authenticatePartner` takes the route's required scope and answers `403 insufficient_scope` after the rate-limit accounting, so a wrongly-scoped key still burns its bucket; the refusal is logged with the route and reason only. `feed` covers `/fingerprints` + `/signals`, `outcomes` covers `/outcomes`. The admin key issue form on `/admin/partners/[partnerId]` gets two checkboxes (default both, at least one required) and the key list shows what each key may do; keys issued before the column existed read as both, in code as in the database default.
- Docs (spec item 4): `docs/product/partner-api.md` now documents the `/signals` contract, the checkpoint rules, tombstones and the forever-kept deletion records, the quality rule, the vPDQ format, key scopes, and the human-review requirement (CDT guidance: a match is a high-signal indicator for review, not automatic removal).

**Decisions made (spec rule 8)**

1. "The checkpoint is the last record's pair" is implemented as the last **raw event's** pair of the page — the same spec's "the checkpoint still advances past it" for a skipped ADD requires exactly that; `has_more` is true while the page was full.
2. An empty page echoes the caller's checkpoint (or the `{t:0,s:0}` start), so the checkpoint never moves on an empty page and can never go backwards for a paging caller.
3. `/fingerprints` applies the same per-frame quality filter to video frames (part of "the full frame list"), but keeps today's no-row-level-quality-filter behaviour for image ADDs — the quality rule is the `/signals` bullet, and the old route's contract was not to change. A video whose frames are all below 50, or missing/unreadable, serves nothing on either feed: production VPDQ rows always store frames (video-fingerprints WP17), and erasure clears `videoFramesEncrypted` only on cases whose sharing has already ended.
4. `vpdqSignalString` mirrors `json.dumps` byte-for-byte (`, ` separator, `.3f` timestamps) rather than semantically-equal JSON, per "formatted exactly as python-threatexchange's vPDQ signal string".
5. The scope check runs after the per-key rate-limit accounting (a wrongly-scoped key still consumes its bucket and cannot probe for free); the security log entry reuses `auth_failed` with `reason: "insufficient_scope"` (no new DB enum value).
6. The admin key list shows each key's scopes — a small extension of the required checkbox form, so an admin can see what an existing key may do.
7. Checkpoint strictness caps: length ≤ 256, `t` ≤ 2100-01-01, `s` < 2^31 — anything outside is malformed, because only Asmita mints checkpoints.
8. The e2e seeds "the dev store" through the real API routes against the e2e dev server and its throwaway Postgres (the e2e harness has no memory store by design), which is stricter than raw row seeding; the spec's "in the dev store" is read as "the app's own dev server store".

- **Deletion keying — the central design decision.** The spec's literal "keys `("pdq", hash)`" (TAT's pattern) cannot work against Asmita's feed, and the e2e proved it live: WP110's serve-time shareability re-check stops serving an ADD once its fingerprint is unshareable, so after a withdrawal the withdrawn fingerprint's hash exists nowhere in the feed (a tombstone carries `hash:null` by design — a withdrawn fingerprint's hash is never served again). A hash-keyed tombstone can therefore never address the entry it must delete — exactly the built-in StopNCII exchange's "deletions quietly never applied" bug class the spec forbids copying (TAT's API, unlike Asmita's, serves the hash on deleted records). Both the ADD and the tombstone are keyed `(signal type, fingerprint id)` — the design the old doc adapter documented ("a deletion is just {fingerprintId: None}") — the signal value rides in the pickled `AsmitaSignalMetadata` (a third field, `signal`, with a default so older pickles stay loadable; the pickle-format stability the spec asks to document is in the class docstring), and `naive_convert_to_signal_type` is overridden to index `metadata.signal` (the simple-updates default would index the id). Consequences, all tested: a tombstone deletes exactly the record its ADD created; two survivors of the same image are two independent records, so one withdrawal never removes the other's signal; a withdrawal costs one record like any other (no refetch, no walk); `report_opinion` still walks the feed once — the ADD history is the only map from a signal value to the fingerprint ids the /outcomes route quotes.

**What was failing, read from the evidence.** The unit checks passed (`ALL CHECKS PASSED` in check.log) and the worker smoke passed (`SMOKE_RC=0`); one Playwright test failed: `tests/e2e/notice-integrity.spec.ts:220` "each link gets its own notice, signed one after another on the review screen" — `page.waitForResponse` for `POST /api/cases/<id>/sign-notice` never fired and the test died at its 180 s budget, with the browser on `/` (the 60 s QuickExit idle sign-out, exactly WP101's signature two days earlier on the sibling test of this same file). The trace WP101 added made this firing legible for the first time: the sign POST left the browser at 23:29:24.893 and was **never answered** — no status, no server-side error, no audit event, so the route handler never ran — while the dev server broadcast `[Fast Refresh] rebuilding` the instant the request arrived and for ~16 s after (two back-to-back Turbopack compile cycles, "done in 2973ms" then "done in 12993ms"). The same trace shows the mechanism on an exchange that survived: the csrf mint at 23:30:20.275 was held 4.9 s and released exactly when the concurrent cycle reported "done in 4736ms". No file changed in the verify clone during the window (checked by mtime), Next is the latest stable (16.4.6, no newer patch), and Turbopack's own HMR client calls these broadcasts "irrelevant `BUILDING` actions … including fully no-op/cached compilations". Conclusion: the dev server held an in-flight request through a compile cycle and silently dropped it — the dev-server stall class WP101 documented; the client's WP101 15 s budget aborted, the survivor's UI recovered, but the test correctly kept waiting for an answer that never came.

**The real defect this firing exposed (and the fix).** After a lost sign exchange, the survivor clicks "Sign and submit" again. Two things can be true server-side: the attempt never landed (the retry signs normally — recoverable), or it **landed and only its answer was lost** — then the retry is answered `409 already_signed`, and every signing screen treated that as a dead-end error: the review screen (`ReviewSignForm.signNotice` / `signHashAdvisory`) showed "This notice has already been signed." and stayed on the same screen, and the case sign page (`SignNoticeForm`) did the same. A survivor whose request succeeded but whose answer was dropped was stranded on a screen for a document she had already signed, with no in-place way forward. The crawl-consent tick already recovers the same refusal the right way (`CrawlConsent.tsx` reloads the state and moves on — WP34), so the sign screens were the outliers. New `asmita/src/lib/sign-retry.ts` makes the decision one pure function: `signAnswer(ok, error)` counts `already_signed` as `{ kind: "signed" }` (the document IS signed — the route answers 409 only when `signedNoticePdf` exists for her own case, and dispatch sends the template pinned at signing, so advancing changes nothing that gets sent), and every other refusal as `{ kind: "error", code }`. All three signing handlers (the review screen's notice and advisory, the case sign page's notice and advisory) decide through it: a real refusal keeps today's error paths unchanged, while `already_signed` falls through to the exact code a successful sign runs — fetch the next notice, or continue to the confirmation. The now-contradictory dead branches (`"review.sign.error.alreadySigned"` / `"sign.error.alreadySigned"` mappings) were removed; the translation keys stay (unused keys are harmless and en/hi parity is what the tests pin).

**Decisions made (spec rule 8)**
