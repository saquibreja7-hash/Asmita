### WP112 done

`services/lab-gend/` (repo root, standalone Python 3.12 service, Apache-2.0 with vendored MIT parts):

- FastAPI + uvicorn, one worker process, one inference worker, bounded queue (max 4 waiting, else 429), 20 s request timeout (504; a timed-out request holds its slot until its work item really finishes, so inference never overlaps).
- Pipeline: decode JPEG/PNG/WebP in memory (<= 10 MB, <= 40 MP, header check before any big allocation) -> YuNet face detection (score >= 0.4, faces >= 48 px on both sides, up to 5 largest) -> GenD's own 5-point template alignment at scale 1.3 (auto target size, exactly the reference inference path) -> HF CLIP 224 preprocessing -> GenD -> p_fake per face. `image_p_fake` is the max over faces, never an average: one swapped face is enough to matter. No face: `{"faces": [], "image_p_fake": null, "status": "no_face"}`, never a score of 0.
- API: `POST /v1/score` (multipart `image`, `Authorization: Bearer <GEND_TOKEN>`) -> `{model: "GenD_CLIP_L_14@<pinned revision>", detector: "YuNet@2023mar", faces: [{box, p_fake}], image_p_fake, status, timings_ms}`; `GET /healthz`. Auth and the body-size cap run in a middleware before any multipart parsing, so oversized or unauthenticated bodies are never parsed.
- Privacy: uploads never touch disk (Starlette's multipart spool threshold is raised above the accepted size and a middleware rejects bigger bodies first); logs carry status, face count and timings only; no image data in error responses. Enforced by tests.
- Weights never committed: `gend/weights_manifest.json` pins every file (GenD `yermandy/GenD_CLIP_L_14@891ce014a0308386c4d7d25b3dcf436a22db5504`, CLIP base `openai/clip-vit-large-patch14@32bd64288804d66eefd0ccbe215aa642df71cc41`, YuNet from OpenCV Zoo at commit 48b10fa505aeb51fbd127fc60a5c660040e823b7) with sha256 + byte size; `scripts/fetch_weights.py` downloads and verifies them (fails closed on any mismatch or unfrozen pin). Multi-stage Dockerfile, final image runs as the non-root `gend` user; the builder downloads the pinned weights at build time.
- InsightFace's `buffalo_l/det_10g.onnx` (what GenD's repo downloads) was NOT used: its pretrained models are non-commercial research only. YuNet (OpenCV Zoo, MIT, verified: "All files in this directory are licensed under MIT License") supplies the box and the same 5 landmarks; the mapping to GenD's template order was verified empirically.
- Vendored minimal GenD code (`gend/modeling.py`, `gend/align.py`) with MIT notice and headers naming the source files and commit 387a42266dd385fbe8f7626c5d3aa03eea3bfaab. Vendoring also avoids `trust_remote_code=True` (the HF checkpoint ships executable model code behind auto_map); loading uses pinned local weights only, never the network.
- ONNX mode: `scripts/export_onnx.py` exports the forward on 1x3x224x224 (dynamic batch); the acceptance gate PASSED on dev-vm: max |p_fake diff| vs PyTorch on 50 synthetic aligned crops 4.23e-06 < 1e-3 on identical tensors, identical decisions at 0.5 on all 50; the full-pipeline comparison (each runtime's own preprocessing) is the same 4.23e-06 because the torch-free CLIP preprocessing (`gend/preprocess.py`) is pixel-identical to the HF processor (tested, including non-square inputs). `GEND_RUNTIME=onnx` runs on onnxruntime alone, no torch.
- Latency (dev-vm, 2 vCPU, median of 20 single-face crops, after warm-up): PyTorch 1942 ms/face (p90 1978), ONNX 1917 ms/face (p90 1989); batch-5 amortised 1839/1933 ms - batching does not help on 2 cores. A 5-face image scores in ~9-10 s here, within the 20 s timeout; a production host will be faster.
- Live checks on dev-vm: uvicorn in the venv (ONNX mode) and the built Docker container both answered healthz, scored a real sample face in ~1.9 s (1 face, p_fake 0.5956 - an FF++ "real" frame, i.e. an uncertain score: a signal for review, not a verdict), returned `no_face` with a null score for a noise image, 415 for junk bytes and 401 without/with a wrong token.

- `box` is [x, y, w, h] integers (YuNet's native form, top-left + size), documented in the README.
- Wrong or missing bearer token -> 401; scoring with no GEND_TOKEN configured -> 503 `not_configured` (not an auth failure: no token could ever match); timeout -> 504; queue full -> 429. /healthz needs no auth (load-balancer liveness).

- The CLIP base weights (1.7 GB) are downloaded even though the GenD checkpoint overwrites the vision tower: the reference code constructs `CLIPModel.from_pretrained(base)` and takes the processor from the same repo; deviating to save bandwidth was not worth diverging from the reference path. The vendored GenD gained one documented deviation (`from_local(gend_dir, clip_base_dir)` pins the CLIP base to a local directory) so loading never reaches the network at runtime.
- The ONNX export is the shipped default (Dockerfile ARG RUNTIME=onnx) because the acceptance gate passed and the image is ~2 GB smaller; GEND_RUNTIME=torch stays the app-level default as the reference runtime.

### WP113 done

GenD in the Lab detector panel, with an honest evaluation measured on this machine.

**What was built**

- Panel adapter (`asmita/src/lib/lab/detectors/adapters.ts`): a fourth row, "GenD (open model, CTU Prague)", calling the WP112 service at `LAB_GEND_URL` with `LAB_GEND_TOKEN` (both env, never committed; either unset → the row shows "not configured" and no image is sent). The exact uploaded bytes (already capped at 10 MB, sniffed to JPEG/PNG/WebP by the route) go to `POST /v1/score`; `image_p_fake` maps onto the panel's 0–100 score and verdict bands like every other row. The service's `status: "no_face"` answer became a first-class result (`{ noFace: true }` → row status `no_face`), rendered as "No face found: this detector only checks face swaps" — never a score of 0 and not an error; it does not count as a disagreement. Fixed error codes (`gend_http_<status>`, `gend_bad_response`, `gend_request_failed`) and the panel's existing 45 s timeout cover the rest.
- Page (`/lab/detectors`): the GenD row carries a one-line note ("Checks face swaps and face reenactment — not every AI-made image.") with paper and code links, a visible "Sources and credits" section listing GenD (authors, WACV 2026, MIT, links) and YuNet (OpenCV Zoo, MIT), and an evaluation-based limits line. Both languages (Hindi machine-translated by Hermes (GLM 5.3), formal register, pending native review; the batch is recorded in `hi-review-status.json`). Design system kept: white/parchment page, teal links, 12 px corners, no coloured border stripes.
- `tools/lab-bench` (E1's harness, reused as the spec requires): a `gend` detector adapter (no downscale — the service must see the degraded bytes exactly), a no-face outcome counted separately from errors in `detect` and its report, the `gend-eval` command and the degradation ladder (`src/degrade.ts`: JPEG 95/75/50/30/10, the E1 WhatsApp-style re-encode at long side 1600 and 1280, max side 128, Gaussian blur sigma 1 and 2 — resolution and blur re-encode losslessly per the E1 rule, JPEG conditions are JPEG), and the bootstrap statistics (`src/gendstats.ts`: ROC-AUC, accuracy at 0.5, no-face rate per class, each with a seeded 2000-replicate percentile 95% CI).
- **The evaluation actually ran on dev-vm.** 44 real portraits vs 44 E1 face-swap composites (the composite builder's own output), all 11 conditions, 968 scored requests against the running WP112 service (ONNX runtime, pinned weights). Aggregate tables and a plain-language reading are in `asmita/docs/lab/gend-eval.md`; in short: AUC 98.4% clean, ~95–96% through WhatsApp-style and moderate JPEG compression, accuracy falling to 58% at JPEG quality 10 and 67% at blur sigma 2, and at max side 128 the service honestly answers "no face" for about half the images instead of guessing. The public limits line on the page states exactly this.
- Docs: `asmita/docs/lab/gend.md` (what it is, the licence chain, deployment — the service runs outside the Worker, the owner chooses the host, dev-vm is for testing only — and the paper's BibTeX), `asmita/docs/lab/gend-eval.md`, a "Detector panel integration" section in `services/lab-gend/README.md`.
- Two latent bugs in the E1 harness surfaced by this first-ever real run of its face locator, fixed in place (the harness had only ever been exercised with injected fake locators): `landmarks.ts` expected `annotations.leftEye`/`rightEye` keys that human 3.3.6 never emits (it annotates eye contours as `[x,y,z]` triples plus a null-placeholder iris key), so every face was silently dropped — now eye centroids come from the iris ring or the lid contours, normalised and validated (`eyePointsOf`, unit-tested); and `faceswap.ts` could extract a patch larger than the real rotated/scaled canvas (rounding) or larger than the target canvas (equal-size portraits), which sharp refuses — both overhangs are now clipped, with a regression test.
