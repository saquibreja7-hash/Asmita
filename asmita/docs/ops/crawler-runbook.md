# Crawler runbook

Status: built, switched off everywhere (`ENABLE_CRAWLER` unset or `false`), 2026-11-16. Nothing here has been deployed. Real survivor fingerprints, real sites and real notices wait for every item in the go-live checklist at the end (ADR 006).

What it is: `docs/adr/006-hash-matching-crawler.md`. The notice path and every refusal code: `docs/product/crawler-notice-flow.md`. The service itself: `crawler/README.md`.

Several steps need the owner's own accounts (Google Cloud, Supabase, Cloudflare). They are written as instructions for him; nobody else runs them.

## 1. Service key

The crawler authenticates to Asmita with a bearer key (`cwk_` + 48 hex). Only its sha256 is stored (`CrawlServiceKey.keyHash`). A missing, wrong or revoked key gets the same 401.

Issue (from `asmita/`, with the owner's database connection, never committed):

```bash
DATABASE_URL=<owner connection> node scripts/issue-crawler-service-key.mjs issue "cloud-run mumbai"
```

The key is printed once. Put it straight into Secret Manager (section 4) and nowhere else: not a chat, an issue, a log or a file in the repository.

List and revoke:

```bash
DATABASE_URL=<owner connection> node scripts/issue-crawler-service-key.mjs list
DATABASE_URL=<owner connection> node scripts/issue-crawler-service-key.mjs revoke <key id>
```

Revoke at once if a key may have leaked, then issue a new one and replace the secret version. A revoked key makes the next run exit 2. Rotate at least whenever someone who saw the key leaves.

## 2. Sources

A SUPER_ADMIN (`crawler:manage`) manages hosts at `/admin/crawl-sources`.

- Add the host name only (for example `news.example-site.org`). Pages are crawled on that host and its subdomains only; links off it are never followed. Images those pages embed may come from other public hosts (CDNs). **Owner decision to confirm:** that embedded images may be fetched from other public hosts (ADR 006 A1).
- A new host starts switched off. Set a page budget (pages a run may fetch, up to 10,000) and a delay between pages (500 ms to 60 s), then switch it on in the confirmation dialog. Both can be edited later.
- Every change is audited (`ADMIN_ACTION`, `crawl_source_*`). Record the reason for each host outside the code (ADR 006 go-live gate 6).
- While `ENABLE_CRAWLER` is off, the list can be read but nothing can be changed (503 `crawler_disabled`).
- Before go-live: test fixture sites only. Never add a real third-party site until the checklist is complete.

**Sites from survivor reports (crawler v2 WP1).** Every source also records how it entered the list (`origin`):

- `admin`: a SUPER_ADMIN added it, as above.
- `reported`: created automatically when a survivor's submitted link, or an analyst-approved crawler finding, names its host. A survivor's link is never turned into a source inside her own request: the hourly retention cron (`/api/cron/purge-expired-urls`, `reportedSourcesCreated` in its answer) takes up to 1000 submitted links not yet checked (`SubmittedUrl.crawlSourceChecked = false`) from all cases, creates the new hosts' sources in one batch (`createdAt` = the sweep time, hosts sorted, one batched audit write with no actor) and marks the links checked, so nothing in the audit log sits next to her own entries. Expect up to an hour between her report and the source appearing. Links stored before this column existed read as checked (the old inline path handled them); to backfill hosts from older reports, an operator can set the column to false for those rows. Only the host is ever copied — never the link, the case or anything identifying her — and the row carries no approver. These sources are enabled from birth with the default budget and delay (section 3), idempotent per host, and they survive the erasure of her account: nothing links them to her. An audit entry (`CRAWL_SOURCE_REPORTED`, on the source itself) records each creation with no actor. Analysing or disabling them works exactly as for admin sources.
- Hosts on the never-crawl list are never created automatically: the built-in list in `asmita/src/lib/crawl-never.ts` (major social platforms, search engines, app stores, webmail, banks and payment sites, government `*.gov.*` and `*.nic.in`, news wires, Asmita's own domains) plus the admin-managed `CrawlBlockedHost` table, where a host matches if it equals an entry or is a subdomain of one. The list is a floor: it stops the automatic paths only, never a SUPER_ADMIN adding a host by hand.

**Bulk import (crawler v2 WP2).** The import box on the same page takes up to 1000 entries, one per line: bare host names or full URLs (the host is taken from a URL, then validated exactly like a single add). Every entry gets its own result — added, already listed (a source exists, or the same host appeared twice in the list), never crawl (built-in list or `CrawlBlockedHost`) or invalid — so a mixed list is reported, never rejected as a whole. Page budget and delay are optional: left blank they come from the env knobs of section 3, and imported sites start switched off unless "switch on immediately" is ticked. Each created source is audited like a single add (`crawl_source_imported`). The request is built to stay within the Worker's per-request limits whatever the list size: a fixed handful of queries, one bulk insert, one batched audit write.

**The never-crawl list (crawler v2 WP2).** The "Never crawl" tab manages the `CrawlBlockedHost` table: add a host with a reason, remove an entry by id (`GET/POST/DELETE /api/admin/crawl-blocked-hosts`, `crawler:manage`). A blocked host blocks its subdomains too, and every change is audited (`crawl_blocked_host_added`, `crawl_blocked_host_removed`). Blocking a host also switches off every existing source for it or a subdomain (whatever its origin; reason `blocked_host` on the admin page, any automatic pause cleared, the ids in the audit entry), the frontier hands out no pages for a blocked host even if its source is switched back on, and the pause sweep never resumes one. A SUPER_ADMIN can still add a blocked host by hand, but it is not crawled while blocked. Unblocking switches nothing back on: an admin re-enables the sources wanted.

**The page frontier (crawler v2 WP3).** The app now owns the list of pages to visit, one `CrawlPage` row per page URL (encrypted at rest, deduplicated per source on a keyed digest, purged after 30 days like findings except rows still due — rows of a switched-off or paused source leave after 30 days even when due — and capped per source by `CRAWLER_FRONTIER_MAX_PAGES_PER_SOURCE`, section 3). The crawler claims batches and reports outcomes over two new service routes, both behind the same bearer key and `ENABLE_CRAWLER` switch (503 when off), 256 KiB bodies, strict validation:

- `POST /api/crawler/frontier/claim` `{ sourceId, limit }` — the next due pages, locked to one crawler for 30 minutes (`FOR UPDATE SKIP LOCKED` on Postgres, so two crawler jobs never fetch the same URL). A source's first claim creates its seed row, `https://<domain>/`. A source hands out nothing more for the day once `pageBudget` pages were fetched that day or are out with a crawler: the claim locks the source row and counts fetched pages plus still-claimed, unreported rows inside its transaction, so two crawler processes together never exceed the budget.
- `POST /api/crawler/frontier/report` `{ sourceId, runId, pages }` — one outcome per claimed page (`fetched` with any new in-scope links, `not_modified`, `gone`, `blocked`, `error`) plus the validators the site returned. The app schedules the next visit: 24 h after a fetched page, doubling after each `not_modified` up to 14 days, 1 h / 6 h / 24 h after errors with the page marked dead after five failures, `gone` dead for good, `blocked` (robots or a 401/403 answer) rechecked after 24 h. Since crawler v3 WP13, narrowed by the review fix, an `error` may carry `failure: "permanent"`: the fetch can never work (a DNS name that does not exist, a definite TLS certificate failure), was not retried in the run, and the row dies only on a second permanent failure at least 24 h after the first — the first one backs off 1 h like any error and is remembered on the row (`CrawlPage.lastPermanentFailAt`, additive migration; a successful visit clears it) — so one bad resolver answer never kills a page. Since crawler v3 WP14 a `gone` can equally mean "this page was a fake 'not found'": within one run the crawler digests each fetched body (whitespace collapsed, digits stripped), and once the same digest has appeared on five or more distinct URLs of one source, further pages with it are reported `gone` with nothing extracted — a site answering every unknown path with the same 200 "not found" page cannot keep the frontier busy forever. The digests are in-memory only, never logged and never sent. Nothing here is audited: it is high-frequency service traffic, not an admin or case action, and the rows carry addresses only, encrypted, never a case or survivor link.

What this means operationally: a killed or crashed crawler loses at most the batch it had claimed — those pages become due again on their own after 30 minutes, and a page the run was mid-way through is redone whole. An admin disabling a source mid-run makes its next claim come back empty and the run moves on. The crawler's own memory for one source is one claimed batch (`FRONTIER_CLAIM_LIMIT`, default 50) plus the report built from it; everything else — the queue, the seen set, the schedule — is the app's.

**Deep coverage (crawler v2 WP4).** The frontier now also holds `sitemap` and `feed` rows, discovered the same way as pages: a source's robots.txt `Sitemap:` lines, sitemap indexes, gzipped sitemaps, image-sitemap entries and RSS/Atom feeds linked from pages. They are claimed, fetched and scheduled exactly like page rows (no second fetch path), so they cost `pageBudget` too — a site's sitemap is deep coverage, not a side door. Two new crawler settings bound the work (see `crawler/README.md`, "Configuration"): `MAX_SITEMAP_URLS` (default 5000 addresses per document) and `MAX_QUERY_VARIANTS_PER_PATH` (default 8; page-number parameters don't count). The crawler also skips obvious non-content (login, cart, search, calendar) and caps query-string traps, so an infinite calendar or `?session=`-style page never enters the frontier at all. Operationally: expect a source's first deep run to fetch noticeably more pages than before as its sitemap is walked; the per-source `pageBudget` still caps the day, and pages parsed as sitemap/feed documents are counted separately in the crawler's `run_summary` (`pagesXml`, `sitemapUrlsTaken`, `feedEntriesTaken`).

**Sitemaps robots.txt does not name (crawler v3 WP9).** When a source's robots.txt names no `Sitemap:` line at all, the crawler probes the conventional paths itself, once per source per run: `/sitemap.xml` on the source host first, `/sitemap_index.xml` only when the first answered nothing usable, and — a source approved on a subdomain — the registrable parent domain's `/sitemap.xml` as well (at most these three fetches). Every probe goes through the same safe-fetch path and robots.txt check as a page fetch and is counted against the source's `pageBudget`; a 404 or a non-XML body is quietly ignored. Of the parent domain, only that one sitemap document is ever fetched — never the parent's pages — and only its `<loc>` entries inside the source's own scope become frontier rows (a probe can therefore add up to three requests per source per run to hosts you approved indirectly through their subdomain). Probes that parse a document reuse the WP4 rules above, and the `run_summary` counts them (`sitemapProbes`).

**Counting the same page once (crawler v3 WP10, tightened by the review fix).** The frontier's dedup digest and the crawler's own dedup key now treat one page's trivial spellings as one page: `http` and `https`, a leading `www.` host and the bare host, a trailing slash on a non-root path, and a final `/index.html`, `/index.htm` or `/index.php` (so `/gallery/`, `/gallery` and `/gallery/index.html` are one row). The rule lives in one shared module (`asmita/src/lib/crawl-page-key.ts`) both sides run, so a page is stored once whatever spelling either side saw; addresses are still fetched and reported exactly as the site wrote them. Rows stored before this change keep the digest they were created with, and (review fix) a link that spells such a row's page differently is checked against the legacy digests of all its spellings at insert time — so no duplicate live row of a page already in the frontier is stored; the old rows simply age out with the 30-day retention. A fetched page's `<link rel="canonical">` target is reported too, as an optional `aliases` field (max 20, in scope only): the app marks any live frontier row for that address dead, and when there is none it stores a dead "tombstone" row on the digest alone, so the canonical address is never fetched just for being canonical and a later link to it cannot create a live row. Tombstone rows are dead: they are never claimed and leave with the retention sweep. Operationally: nothing changes for the admin pages — the count-once rule only shrinks the fetches a duplicated site layout would otherwise cause, and a canonical that names an address outside the source's host is ignored (it is never a discovery either).

**Crawl the useful pages first (crawler v3 WP11, tightened by the review fix).** Every `CrawlPage` row now carries a `priority` (additive migration; existing rows were backfilled by a second data migration) and a claim hands out the due rows of a source in priority order, then by how long they have been due (`ORDER BY priority, nextDueAt` on all three backends). The report sets a new row's priority from what the crawler found: sitemap 10, feed 20, a pagination link 30 (the crawler flags `rel="next"` and its siblings on the reported link), any other page 50 plus 10 per depth level, capped at 100. A sitemap entry whose `<lastmod>` is a strict ISO date newer than that row's last fetch gets priority 5 and becomes due immediately, so a page the site says changed is crawled without waiting out its own schedule; a row never fetched (already due), a dead row, and a row the very same report fetched keep their schedule. The review fix tightened three edges: the seed row is stored at 50 (the depth-0 page value) and the backfill migration gave existing rows the same rule, a reported lastmod is clamped to now before it is compared (a site cannot outrank every honest page by writing a future date), and a successful visit resets the row's priority to its kind/depth value, so a lastmod jump is one-shot instead of keeping the row at the front of the queue forever. The crawler itself stays priority-blind — it only reports the pagination flag and the normalised `<lastmod>`, never a priority — so a hostile report cannot reorder the queue beyond the fixed kind rules. Operationally: a source's sitemap and feeds are crawled before its individual pages, and no admin page or env var changes.
**Galleries in frames and components (crawler v3 WP16).** A page's `<iframe src>` and `<frame src>` are now followed as ordinary page links, so a gallery that lives inside a frame is claimed as its own page and costs `pageBudget` like any other — under the same scope rule (an off-scope frame is never fetched; its host is reported like any out-of-scope link, see WP5 above), the same non-content and query-cap skips, and `nofollow`. For sources rendered in the browser (WP7), the render also walks every frame of the page and every open shadow root after the page has settled, and loads the images the page's own scripts never asked for (a lazy loader inside an iframe or a web component that never runs in a headless browser) — through the same proxy, robots check and per-page caps as the page's own image requests. No new setting; the per-page caps bound it. Operationally: framed gallery pages appear as their own rows in the frontier, and a `render = browser` source may report image findings from addresses its main document never names — the page address on the finding is still the claimed page.

**Discovered sites (crawler v2 WP5).** The crawler now reports the hosts of out-of-scope links it sees on in-scope pages — hostnames only, never links — over `POST /api/crawler/discoveries`, deduplicated per run and capped at `MAX_DISCOVERY_HOSTS` (default 1000; 0 switches discovery off). The app, not the crawler, decides what becomes a site: never-crawl hosts and hosts that are already sources are skipped; the rest become a `DISCOVERED` source one hop deeper than the site that linked it (`hops`, `discoveredFromId`), with the `CRAWLER_DISCOVERED_PAGE_BUDGET` budget. Such a source is switched on automatically while its hops are within `CRAWLER_MAX_DISCOVERY_HOPS` (default 2) and at most `CRAWLER_MAX_NEW_SITES_PER_DAY` (default 200) are switched on per UTC day — everything past either limit is stored switched off with the reason shown on the admin page. The crawler never fetches a discovered host until a later run's `GET /sources` lists it. Two automatic rules manage a discovered site's life: a match under it promotes it (`hops` reset to 0, budget raised to `CRAWLER_REPORTED_PAGE_BUDGET`, audited), and the hourly retention cron's sweep pauses one whose page budget was spent three UTC days running without a single finding (counted from `CrawlSourceDay`, the per-source per-day fetch counter the frontier report keeps, because a revisit overwrites a page's `lastFetchedAt`; the sweep prunes counters older than a week) — switched off for 30 days (`pausedUntil`, `pauseReason`), then switched back on by the same sweep. An admin switching a site on or off clears an automatic pause (switching on also clears the stored disabled reason) and owns it from there: the sweep only resumes a site that is still switched off and still carries its pause, so an admin's "off" is never undone. Every creation, promotion, pause and resume is audited (`CRAWL_SOURCE_DISCOVERED` / `_PROMOTED` / `_PAUSED` / `_RESUMED`); the "Crawler sites" page shows a discovered site's parent and why it is off. The reporting parent must itself be enabled at report time, so a site an admin switched off mid-run stops growing the list.

**In-page redirects (crawler v3 WP12).** The crawler now follows redirects that live in the page body, not the protocol. On the static fetch path, a page whose HTML carries a qualifying `<meta http-equiv="refresh">` — a target address and a delay of up to 10 seconds — is followed like an HTTP redirect: every hop is re-checked (the source's host scope, robots.txt, the address policy), it counts inside the same five-hop redirect budget, and it never takes a fetch off the source's host. The content extracted is the target's, and findings keep the page address as claimed; a refresh slower than 10 seconds, or one without a target, is treated as page content instead. For sources set to `render = auto`, a page that is a tiny script-only stub — under 2 KiB of visible text, at least one script, no image candidates, no links — is sent to Chromium, because such pages are usually JavaScript redirects (`location.replace`) or app shells whose content only exists after rendering. Sources with `render = browser` leave meta refreshes to Chromium itself. Nothing changes for the app or the frontier contract; no new environment variables.

## 4. Build and deploy (owner, Google Cloud)

Region: Mumbai, `asia-south1` (the pool is survivor data and stays in India, ADR 004). A Cloud Run **job**, not a service.

1. Build from the repository root (the image includes the read-only PDQ module from `asmita/`):

   ```bash
   docker build -f crawler/Dockerfile -t asia-south1-docker.pkg.dev/<project>/asmita/crawler:<git sha> .
   docker run --rm --read-only --network none asia-south1-docker.pkg.dev/<project>/asmita/crawler:<git sha> run   # must exit 1: no configuration
   docker push asia-south1-docker.pkg.dev/<project>/asmita/crawler:<git sha>
   ```

   Use the commit sha as the tag, never `latest`. Crawler CI builds the same image and runs it with `--read-only`.

2. Secret: create `crawler-service-key` in Secret Manager in the same project and add the key from section 1 as a version. Create a service account for the job (for example `asmita-crawler@<project>.iam.gserviceaccount.com`) with only `roles/secretmanager.secretAccessor` on that one secret. No other roles.

3. Job:

   ```bash
   gcloud run jobs create asmita-crawler \
     --region asia-south1 \
     --image asia-south1-docker.pkg.dev/<project>/asmita/crawler:<git sha> \
     --service-account asmita-crawler@<project>.iam.gserviceaccount.com \
     --tasks 1 --max-retries 0 --task-timeout 3600s --memory 2Gi --cpu 1 \
     --set-secrets /secrets/crawler-service-key=crawler-service-key:latest \
     --set-env-vars CRAWLER_SERVICE_KEY_FILE=/secrets/crawler-service-key,ASMITA_API_URL=https://<production origin>,CRAWLER_USER_AGENT="<agent>",MAX_RUN_MINUTES=50
   ```

   The key is mounted as a file, not an env var. The `--set-secrets <path>=<secret>:<version>` file form is written from memory and has not been run: check it against the current Cloud Run jobs documentation before use.

   What the decoder isolation gives and does not give (`crawler/README.md`, "Decoder isolation"): decoder children never receive the pool, the key or URLs, cannot write files or spawn processes from JavaScript, and are recycled by the parent. They run as the same OS user as the crawler, and native code in an exploited decoder is not bound by Node's permission model, so it could reach the network, read the key file and, where the kernel allows same-user tracing, the parent's memory. Before go-live, harden the deployment (checklist below): run the decoder children under a separate UID or a syscall sandbox (seccomp, gVisor, nsjail) with no network, the key file readable only by the crawler's own UID. Cloud Run's sandbox (gVisor in the first-generation execution environment, a microVM in the second) wraps the whole container; it does not separate the decoder from the crawler inside it, and Cloud Run has no per-process egress control.

   Browser rendering (crawler v2 WP7) adds a third child process, headless Chromium, for sources an admin set to `render = BROWSER` (and `AUTO` pages that need it). Its traffic goes through an in-process proxy with the same address policy as every other fetch, robots.txt is honoured per request, and its throwaway profile lives in `/dev/shm` (`BROWSER_TMP_DIR`) — nothing reaches disk. Since WP7 the runtime image is `node:22-bookworm-slim` with Chromium installed by playwright-core's own CLI (the browser revision is pinned by the lockfile); it is no longer distroless, because Chromium's shared-library set is not maintainable there.

   **The browser sandbox (WP25).** Chromium now runs with its own sandbox ON — no `--no-sandbox` is ever passed when the sandbox works. Its Linux sandbox needs unprivileged user namespaces, which a container runtime may refuse (Docker's default seccomp profile denies them to a non-root user; Chromium also refuses to run sandboxed as root). The crawler therefore self-tests at the first browser launch of a run: the verdict lands in the `run_summary` line as `browser.sandboxTested` / `browser.sandboxOn` / `browser.workerUid` (booleans and ids only, never a URL). Sandbox unavailable → rendering is disabled for the run automatically: BROWSER pages report `error` under the `browser_sandbox_unavailable` code, AUTO pages fall back to their static result. The only override is `CRAWLER_ALLOW_UNSANDBOXED_BROWSER=true` — local development only, never a deployment.

   **Checking the sandbox status in production** (from the run summary of any run that had a browser source):

   - `browser.sandboxTested: false` — no page needed a browser this run; there is no verdict yet.
   - `browser.sandboxTested: true, browser.sandboxOn: true` — the sandbox works; browser sources may be enabled (within the go-live checklist).
   - `browser.sandboxTested: true, browser.sandboxOn: false` — the runtime refused the sandbox; rendering was disabled (or, if the dev override was somehow set, it rendered unsandboxed — check that `CRAWLER_ALLOW_UNSANDBOXED_BROWSER` is unset). Fix the runtime (below) rather than accepting this.
   - `browser.workerUid` — the uid the browser worker ran as; in the container image it must be `30000` (`browser-worker`), different from the crawler's user (`1000`, `node`). `-1` means no worker answered (no browser was needed, or the sandbox was refused before a worker could start). If it equals the crawler's uid outside the image, the uid separation is not active — only acceptable outside the container.

   To get the answer without enabling any browser source, run the standalone probe in the image (no key, no config, no network):

   ```bash
   docker run --rm --read-only --network none <image> node dist/sandbox-check.js
   # {"event":"sandbox_check","sandboxTested":true,"sandboxOn":true,"workerUid":30000}   exit 0
   # {"event":"sandbox_check","sandboxTested":true,"sandboxOn":false,"code":"browser_sandbox_unavailable"}   exit 1
   ```

   To make a container runtime allow the sandbox, run the container with `--security-opt seccomp=crawler/docker/seccomp-userns.json` (Docker's default seccomp profile plus unprivileged user namespaces; Cloud Run's job cannot be given a custom seccomp profile through `gcloud`, so on Cloud Run the sandbox verdict depends on the platform's own sandbox and must be read from the run summary — if it says off, browser rendering stays off there). `scripts/docker-sandbox-check.sh` (repository root) proves both modes against real Docker.

   **Defence in depth in the image, either way.** The browser worker never holds the service key: it is spawned with a fixed five-name environment (no `CRAWLER_SERVICE_KEY`, no `CRAWLER_SERVICE_KEY_FILE`, nothing inherited from the parent) and, in the container image, it is dropped onto the separate `browser-worker` user (uid 30000) by a tiny setuid helper (`/usr/local/bin/asmita-browser-drop`, the `chrome-sandbox` pattern: it switches users and execs, never running anything as root). The key file is owned by the crawler's user with mode 0400, so the worker's uid cannot read it — nor the parent's `/proc/<pid>/environ`. If a platform starts the container as root, the image's entrypoint hands the key file to the crawler's user and drops privileges once (`setpriv`); nothing keeps root afterwards. Give the job more memory when browser sources are enabled, and check the platform's `/dev/shm` size (Docker: `--shm-size=1g`; `crawler/README.md`, "Browser rendering").

   Since crawler v3 WP15 the browser is lighter, with no operator switch to set: font requests, audio and video media, and a small built-in list of advertising/analytics hosts (written in the worker's code, never an image or video CDN) are aborted before any routing work — never fetched, never counted against the per-page request cap — and the fixed wait after scrolling is replaced by a network-quiet wait (no request in flight for 500 ms, bounded by the page deadline), so slow lazy-loaders are waited for without slowing down pages that finish quickly.

   Video fingerprints (video-fingerprints spec WP20): `/api/crawler/pool` now serves an approved, consented video fingerprint (algorithm vPDQ) as its own entry `{ id, kind: "video", frames }` — the frame hashes her browser computed on her device, never qualities, timestamps or bytes. The crawler indexes the frames in memory (multi-index hashing, `crawler/README.md` "Matching") and reports an image within the match threshold of a frame — a poster or preview — as a finding against the video's pool id, through the unchanged finding contract: every match is reviewed by a person, and withdrawal or erasure takes a video out of the pool exactly like an image fingerprint (the next pool re-sync, at most an hour into a run). No operator switch: no new env var, migration or admin-UI change. Two things to watch: the pool response grows with consented videos (each contributes at most 1,000 frame hashes, about 64 KiB of JSON, and the crawler caps the whole response at 64 MiB), and the run summary gains a `videoMatches` count beside `matches` — counts only, no frame hash is ever logged. Phase 2 never fetches video bytes: only images are downloaded and decoded, in the existing isolated decoder child under the existing size and time budgets.

   Video previews (video-fingerprints spec WP21), also no operator switch: the crawler now treats a page's video previews as image candidates and hashes them like any image — a `<video poster>`, the `og:image` of a page that declares an `og:video`, a JSON-LD `VideoObject.thumbnailUrl`, a video-sitemap `<video:thumbnail_loc>` (hashed for its sitemap page), and a preview sprite sheet: one image holding a grid of the video's thumbnails, recognised by its address naming a sprite or storyboard and split into its tiles inside the same isolated decoder child (one decode, one hash per tile, at most 100 tiles, each tile matched against image fingerprints and video frames like an image of its own). Several tiles of one sprite hitting the same video are one finding, reviewed by a person like every other; the run summary counts `videoPreviews` (preview-tagged images hashed) and `spriteTiles` beside `videoMatches` — counts only. The split is a heuristic with documented limits (`crawler/README.md`, "Known limits"): a mis-split sprite costs a missed match on that file, never a wrong finding, and still no video bytes are ever fetched.

   SSCD, the second matching layer (ADR 008, WP28) — **off by default**; when `ENABLE_SSCD` is `true` on the app *and* the crawler, images PDQ did not match are also compared with SSCD embeddings of **analyst-confirmed copies**, to find altered versions (crops, filters, screenshot rescales, mirrors — what PDQ does not survive). How it runs: when an analyst approves a finding, the crawler embeds that confirmed image the next time it holds its bytes (a PDQ match on a revisit) and offers the vector to `POST /api/crawler/embeddings`; the app stores it encrypted (`FindingEmbedding`, RLS like every table) only for that analyst-confirmed finding, and serves it back through the pool under the same consent gating as the PDQ hashes. The crawler keeps the vectors in memory for the run and matches by brute-force cosine (fine at Asmita's scale; the bound is in ADR 008). Scope: only sources where a finding was already accepted (`SSCD_SCOPE=matched_sources`, the default; `all` widens it), capped at `SSCD_MAX_PER_RUN` inferences a run. Every hit becomes a normal finding for the same analyst review — the finding says which layer matched (`method`), an SSCD finding always needs the second reviewer, and a borderline PDQ match (distance 25-31) carries an SSCD score the analyst sees (information only, never an automatic accept or reject). Withdrawing the authorisation, rejecting the fingerprint or erasing the case deletes its embeddings at once, and the pool stops serving them on the next build. Logs carry counts only (`sscdInferences`, `sscdMatches`, `sscdSkippedBudget`, `sscdSkippedScope`, embedding offer counts) — never a vector. Operator checklist for switching it on (both sides must agree on `SSCD_MODEL_ID`/`SSCD_MODEL_VERSION`, defaults `sscd_disc_mixup`/`onnx-1`):

   - App: set `ENABLE_SSCD=true` (Worker var). The pool starts serving embeddings, `/api/crawler/sources` starts flagging matched sources, and the embeddings route opens.
   - Crawler: set `ENABLE_SSCD=true` and `SSCD_MODEL_FILE=/app/models/sscd_disc_mixup.onnx` (the image downloads the pinned, sha256-checked weights at build time). Give the job more memory while the SSCD child is resident (4 Gi recommended).
   - The crawl authorisation sentence for this (ADR 008) is seeded **unreviewed** and needs the owner's — and counsel's — approval before survivors sign it; nothing about the layer is live for survivors until then.
   - The evaluation numbers (PDQ vs PDQ+SSCD recall, the threshold, seconds per image) are in ADR 008; the script is `crawler/scripts/eval-sscd.ts` and needs the pinned weights.

   Read-only filesystem: the image is built for `docker run --read-only` (non-root, `TMPDIR` pointing at a path that does not exist; the browser worker gets the memory-backed `BROWSER_TMP_DIR` instead), and the process never writes. Cloud Run's own filesystem is in-memory and cannot be mounted read-only, so the guarantee comes from the image and the tests, verified with `--read-only` in CI. Do not attach the job to a VPC with private routes.

4. Schedule with Cloud Scheduler: a dedicated invoker service account with `roles/run.invoker` on the job only, calling the job's `run` endpoint once a night (IST). The pool must be re-synced at least hourly within a run, which the crawler does itself.

5. Running it continuously (crawler v2 WP6). The crawler has a second command, `node dist/main.js run --loop`: it repeats a full pass — list sources, claim, fetch, hash, report — until stopped, picks up a source an admin switches on mid-run on the next pass's source listing, sleeps `LOOP_IDLE_SECONDS` (default 60 s) whenever a pass finds nothing due, and logs a `run_progress` line every `PROGRESS_LOG_SECONDS` (sources active, pages claimed/fetched/not-modified, new URLs, new hosts reported, images hashed, matches). SIGTERM ends the current pass cleanly (exit 0); any other exit code ends the loop with that code. Two supported shapes:

   - **VM container with a restart policy** (the always-on form): a small VM in `asia-south1` running the same image with `docker run -d --restart unless-stopped --read-only --network <egress-only> ...` and the same key file, env vars and `run --loop` command. The restart policy is the retry cadence for every non-zero exit; systemd or a managed instance group can replace Docker if preferred. Nothing else changes: the process writes nothing and needs only outbound internet.
   - **Short-cadence job (the Cloud-native form):** keep the Cloud Run *job* above and have Cloud Scheduler call it every 15–30 minutes instead of nightly. Overlapping invocations are safe by design — frontier claims are exclusive for 30 minutes (`FOR UPDATE SKIP LOCKED`, WP3) — so near-continuous coverage needs no new moving parts. Each invocation is the ordinary one-shot `run`.

   A Cloud Run **service** is deliberately not offered for the loop: Cloud Run requires a service's container to listen on a port (it fails deployment otherwise), the crawler listens on nothing by design (no inbound surface), and adding a listener just to pass a health check would grow its attack surface for no crawl benefit. If that ever changes, the decision belongs in `crawler/README.md`, not here.

6. Updating: build and push a new sha, then `gcloud run jobs update asmita-crawler --region asia-south1 --image <new image>`.

## 5. Exit codes and what to do

Each run ends with a `run_summary` log line carrying `exitCode` and a `problems` object. Logs never contain addresses, fingerprints or image data.

| Code | Meaning | Do this |
|-|-|-|
| 0 | Clean run, or the app has the crawler switched off (503) | Nothing. If findings were expected and none came, check `ENABLE_CRAWLER` and that sources are on |
| 1 | Bad configuration or unexpected failure | Read the summary's error code; fix the env vars or secret; rerun once by hand |
| 2 | Service key rejected (401/403) | The key was revoked, mistyped, or `ENABLE_CRAWLER` and the key do not match the environment. Issue a new key (section 1), add a secret version, rerun |
| 3 | Findings undelivered (Asmita API down past retries) | Check the Worker and database health; the next run reports the same matches again |
| 4 | Contract error: Asmita refused a request as malformed (400) | A crawler and app version mismatch. Do not rerun repeatedly; deploy matching versions (the crawler's client and the app's findings route must agree) |
| 5 | Pool could not be re-synced for 60 minutes; run stopped | Check the Worker and `/api/crawler/pool` (needs the key and `ENABLE_CRAWLER=true`); the stop is deliberate so withdrawn fingerprints never keep matching |
| 64 | Bad command line | The job's command or args were changed; restore `run` |

A failing site (down, robots.txt unreachable, timeouts) is not a run failure; it is counted in the summary. Since crawler v3 WP13 the summary splits fetch failures by class: `failures.permanent` (a DNS name that does not exist, a definite TLS certificate failure — those pages are reported `error` with the `permanent` hint, never retried in the run, and their rows die only on a second permanent failure at least 24 h after the first; environment-type certificate failures such as a missing local issuer count as temporary) and `failures.temporary` (timeouts, connection resets, 5xx — the usual 1 h / 6 h / 24 h backoff), plus `homePermanentFailures`: how many sources' home pages failed permanently this run, one count per site, never a hostname. A non-zero `homePermanentFailures` that repeats run after run points at sites that have been abandoned or whose certificates are broken — remove them from the list or fix them at their origin; their rows die after the second permanent failure a day later either way. Since crawler v3 WP14 the summary also counts `pagesSoft404`: pages whose body (normalised: whitespace collapsed, digits stripped) had already appeared on five or more distinct URLs of the same source this run — fake "not found" pages served with a 200, reported `gone` with nothing extracted. A high `pagesSoft404` on a source usually means the site answers unknown paths with one "not found" page and something keeps linking them; those rows are dead for good, which is the intended cut. If a source's genuinely different pages all collapsed into it (same template, only ids differing), that is a known limit of the digit-blind digest — see the crawler README's known limits before re-adding such a source.

For a `--loop` deployment (section 4, step 5) the same codes decide the process. Exit 0 starts the next pass — including when the app has the crawler switched off: each such pass ends immediately and the loop polls every `LOOP_IDLE_SECONDS` until the switch comes back on, so a switched-off crawler is quiet, not dead. Any other code ends the loop and the restart policy retries; a config error (1) or a bad key (2) will loop-crash until a human fixes the env or the secret, which is the intended signal.

## 6. Analyst work

At `/admin/findings` (`findings:review`). Interim safety guidance is on every finding page; the written procedures in the checklist replace it.

- An address is shown only after a reason is given; each reveal is logged and audited and limited to 20 an hour.
- Above distance 20 a second, different analyst must approve.
- The notice preview shows both addresses, so it counts as a reveal (logged, audited, 20 an hour). The analyst confirms that before previewing; nothing previews by itself. Send sends exactly the previewed notice, and only while the preview is on screen: it is cleared, PDF included, after 2 minutes without activity.
- Downloading the PDF asks for confirmation first: it holds both addresses and must not be kept on a personal device. The file name carries no case reference. Copying a revealed address carries the same caution.

**Review labels (review labels WP37).** On every finding page an analyst can set or clear three labels — "Looks AI-made", "Sexual content", "Possible minor" — our own simple fields, each recording who set it and when, audited like every other finding action (`CRAWL_FINDING_LABEL_SET` / `CRAWL_FINDING_LABEL_CLEARED`, `POST /api/admin/findings/[id]/labels`). The findings list can be filtered by label (`?label=ai-made|sexual|possible-minor`) and by the separate minor-protocol status, and the crawler overview counts findings by label.

- "Looks AI-made" and "Sexual content" are review notes for the record: any analyst sets or clears them.
- "Possible minor" is a **safety switch**, not a note. Setting it stops the adult flow for that finding at once: it cannot be approved or dismissed, no representative notice can be prepared or sent, and it leaves the review queue for the minors protocol — the finding moves to the separate `MINOR_PROTOCOL` review state (and back to `CANDIDATE` or `APPROVED` only when the label is cleared). Until the written POCSO procedure exists (go-live gate 3, ADR 006), this state **is** the minors handling for crawler findings: it marks the finding for that protocol, and the analyst still tells the SUPER_ADMIN straight away, as the interim guidance says. Clearing the label needs a **different admin** than the one who set it and a **written reason** (stored on the finding and in the audit log); nothing else puts the finding back into the adult flow. A dismissed finding keeps its dismissal: the label is recorded on it, and clearing it restores nothing.

**Watch findings (WP22 "Watch for my images").** A finding can belong to a watch: she fingerprinted her images without filing a complaint, and a watch-only authorisation (`CrawlConsent.scope = WATCH_ONLY`) permits searching and alerting her, nothing else. Review such a finding exactly as any other; on final approval the found link is added and she gets an email that carries only her case reference. While the case is still a watch, the console shows "Watch only: she has not asked for removal yet" and the notice step refuses `watch_only_consent` — nothing can be sent. When she chooses "Take it down", the watch becomes a case, she signs the full authorisation on the spot, and the notice path opens for that finding as usual. Watches never appear in the Needs action queues except under "Found copies to review" (a found copy awaiting review); their fingerprints are reviewed from the Fingerprints queue like any others.

**Crawler overview (crawler v2 WP8).** `/admin/crawler` (`findings:review`, reads only, works with the crawler off) summarises how the crawler's work stands: sites by origin and state, pages crawled today (the same UTC-day count a source's daily `pageBudget` uses), the frontier queue (live, pending, due, claimed, scheduled, dead), sites discovered today, matches awaiting review, the last run the app saw, and page outcomes by the code the crawler reported. Since WP37 it also counts findings carrying each analyst label and how many sit in the minors protocol. It renders from `GET /api/admin/crawler/stats`, an address-free aggregate — counts, timestamps and one run id only, never a host, URL, fingerprint or case reference — computed in the database on the memory, Kysely and Prisma paths (`src/lib/crawl-stats.ts`). Two honest limits are printed on the page itself: the app can name a run only through the matches it reported (a run that found nothing leaves no run id; the crawler's own `run_summary` log line is the full record), and the outcome codes are the page statuses of the frontier report, not the crawler's finer error codes.

## 7. Kill switch

Set `ENABLE_CRAWLER=false` (or remove it) on the Worker and deploy. At once:

- the pool, sources and findings routes answer 503, so a running crawler stops matching and exits 0;
- analysts can still read findings and their history, but review, notices and source changes return 503 `crawler_disabled`;
- survivors cannot sign a new authorisation, and can still withdraw.

To stop one site only, switch its source off. To stop the job running at all, pause the Cloud Scheduler trigger; to stop a `--loop` deployment, stop the VM container or the Scheduler trigger behind the short-cadence job (section 4, step 5). To cut off a crawler whose key may have leaked, revoke the key (section 1).

## 8. Unconfirmed send

There is no admin action to resolve an unconfirmed send, for crawler notices or for survivor notices (`email_already_sent` on `/api/notices/dispatch` has none either). One was not invented. The console tells the analyst to stop and ask the SUPER_ADMIN.

What the codes mean:

- `dispatch_in_progress`: another request holds the claim. Usually a double click or two analysts at once; wait a minute and reload.
- `link_now_survivor_owned`: the survivor reported the same page herself just before the send, so the link became hers. Nothing was sent; she signs her own notice for it. Not an unconfirmed send.
- `email_already_sent`: Resend already accepted this exact notice under its idempotency key. Nothing is sent twice. If the link still shows as not sent after a reload, it reached Resend without being recorded.
- `earlier_attempt_unconfirmed`: a notice was stored on the link as a claim (`representativeNoticePdf`, `representativeNoticeDigest`) but never recorded as sent, and the notice the analyst would send now differs (usually because the date changed). It may have reached the platform.

Resolution, by the owner only:

1. Do not retry from the console.
2. In the Resend dashboard, look for an email to the platform's grievance address with the case reference in the subject, around the time of the attempt (the admin access log shows the preview time). The idempotency key is `notice:` followed by a sha256 of the case id, link id and recipient.
3. If Resend shows it was sent: the platform has the notice. Record that in the incident log with the Resend message id, tell the reviewer, and leave the link as it is until a recording procedure is agreed. Do not send it again.
4. If Resend shows nothing for that recipient and case: with a second person present, clear the claim on that one `SubmittedUrl` row (set the seven `representative*` fields to null where `id` is the link and no `Notice` row exists for it), note it in the incident log, then the analyst previews and sends again.
5. Either way, write an incident entry (`docs/ops/incident-runbooks.md`).

## 10. Removal re-checks (watch-and-verify WP23)

When one of her links becomes REMOVED — she marks it removed, or an admin records a platform reply of REMOVED — three re-checks are scheduled: +1 day, +3 days and +7 days. There is no new cron trigger: the sweep rides the existing hourly `/api/cron/purge-expired-urls`, whose answer now also carries `verificationsEnqueued`, `verificationsResolved` and `verificationsStillOnline`. If the link is no longer removed when a check comes due, the checks still waiting for it are dropped.

Each due check is put into the crawler frontier as a priority row for its host's source, creating a REPORTED source through the existing rules when none exists; the crawler then visits the page like any other, through the same claim/report path — there is no second fetch path. While `ENABLE_CRAWLER` is off the sweep does nothing and checks wait as PENDING. A never-crawl host answers UNKNOWN at once, with no source and no frontier row. A check whose link lost its address to the 30-day retention resolves UNKNOWN, and erasure deletes a case's checks with its links.

Outcome rules, from the crawler's report on that page row:

- page gone or blocked (404/410, robots, 401/403) → GONE;
- page fetched with no finding, while her fingerprints are live in the pool → GONE (the image is no longer there);
- page fetched without pool fingerprints, a not-modified answer (images not re-hashed), or a page that never answered within 7 days of queuing → UNKNOWN;
- a finding for that page on her case since the check was queued → STILL_ONLINE, whatever the page row says.

STILL_ONLINE returns the link to the notice-sent state, so the existing escalation sweep follows up on its own schedule; the episode's remaining checks are dropped, a `CONTENT_STILL_ONLINE` audit entry is written, and she receives an email carrying only her case reference and a sign-in prompt.

Operationally: resolution of a fetched page waits two hours after the crawler's report, so findings still in flight can arrive; at most 200 checks are enqueued and 200 resolved per hourly pass, the rest wait an hour; the `LinkVerification` table stores no URL — a check works from the `SubmittedUrl` it references. The admin case page shows each link's removal-check history; her case page shows "Verified removed (checked N times)" after three GONE results and "Still online: we have followed up" after a still-online check.

Legal: the still-online email wording and the whole re-check behaviour — re-visiting pages after a takedown to verify removal — are new and unreviewed. Counsel must read them before real use; both are on the spec's "For legal sign-off before real use" list (`docs/product/watch-and-verify-spec.md`).

## 11. Re-upload watch (watch-and-verify WP24)

When a case is resolved — or every link on it is verified removed by the WP23 re-checks — her live crawl authorisation gains a 12-month window (`CrawlConsent.watchUntil`), and while it runs the crawler keeps matching her fingerprints even though the case is closed. There is no new cron trigger: the sweep rides the existing hourly `/api/cron/purge-expired-urls`, whose answer now also carries `reuploadWatchesStarted`; at most 200 windows start per hourly pass, and the first start wins (a later resolution never moves the date). Starting the window is part of the case's record, not a crawl action, so the sweep runs whatever `ENABLE_CRAWLER` says.

What the window does:

- the pool keeps her approved fingerprints only while the case is open or `now < watchUntil` (`src/lib/crawl-pool.ts`); after that they leave the pool exactly as a withdrawal's do, without touching the consent itself, and a crawler report under one of them is refused (`fingerprint_not_accepted`). The WP23 image-level check follows the same rule.
- no new site is fetched and no source is added for her: the sources created from her reported links stay as they are, and a re-upload is found on sites the crawler already visits.
- a re-upload found and approved by an analyst becomes a link on her case like any finding — it appears under "Found by Asmita" on her dashboard and follows the existing representative-notice path, because her full authorisation covers it — and she receives an email carrying only her case reference and a sign-in prompt (one email per approved finding, sent at final approval while the window runs; an open case never triggers it).

Her case page shows "Watching for re-uploads until <date>" in place of the open-case search copy while the window runs, with "Stop watching" — which withdraws the authorisation with the existing effects (fingerprints leave the pool at once, unreviewed possible matches are deleted, unsent crawler links are stopped).

Operationally: the window is a bare nullable date on the consent (migration `20261119120000_crawl_consent_watch_until`), the sweep decides from the case status and GONE-check counts only (no address is read), and a `CRAWL_WATCH_STARTED` audit entry records the consent id and the window's end. Erasure needs no new rule: the column lives on the consent, which erasure already deletes.

Legal: the re-upload alert email wording and the 12-month watch itself are new and unreviewed. Counsel must read them before real use; both are on the spec's "For legal sign-off before real use" list (`docs/product/watch-and-verify-spec.md`).
