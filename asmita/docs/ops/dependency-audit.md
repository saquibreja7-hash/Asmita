# Dependency audit

The CI "Dependency audit" job (`.github/workflows/ci.yml`, job `security-audit`) installs `asmita/` with `npm ci` and runs `npm audit --audit-level=high --omit=dev` (script `security:audit` in `asmita/package.json`). Only `asmita/` is covered; `crawler/` and `tools/` have no audit step in CI. This page records what changed in that audit and why. An advisory with no patched version at all is recorded here, never silenced in the workflow; the audit command and its threshold are not loosened.

## 2026-11-20 — WP78: audit green again (branch `fix/dependency-audit`)

The check had been failing on published npm advisories. npm counts every package in a vulnerable dependency chain, so the report read "8 vulnerabilities (5 moderate, 3 high)" while the two underlying advisories were these. Both were fixed with npm `overrides` in `asmita/package.json` — the smallest change, because every package that pulls the vulnerable one pins it exactly, so no upgrade of a direct dependency could reach a patched version — and the lockfile was regenerated with Node 22. After a fresh `npm ci`, `npm run security:audit` in `asmita/` reports **found 0 vulnerabilities**.

- **effect** [GHSA-7589-6fvf-x4pw](https://github.com/advisories/GHSA-7589-6fvf-x4pw) — high, ReDoS in `Schema.TemplateLiteral` compiled regex, vulnerable `<=3.22.0`. Reached through `@prisma/config` (the prisma CLI's config loader, a dev chain), which pins effect `3.20.0` exactly; prisma 7.10.0 and 7.10.1 both still do, so no upgrade path existed. The old lockfile also did not flag the package dev, so `--omit=dev` audited it anyway. Fix: override `"effect": "^3.22.5"`; effect 3.22.5 is installed and the regenerated lockfile flags it `devOptional`. Verified: `prisma generate`, `prisma validate`, lint, type-check, the test suite and `npm run build` all pass with it.
- **fflate** [GHSA-px8p-9vwx-vf98](https://github.com/advisories/GHSA-px8p-9vwx-vf98) — moderate, `unzipSync` can enter an infinite loop parsing malformed ZIP64 archives, vulnerable `>=0.7.0 <0.7.5`. One vulnerable copy: satori's nested fflate 0.7.3, used for OG image generation via `@vercel/og` under `vinext` (a production path). satori 0.33.5 pins fflate `0.7.3` exactly — even the newest satori (0.63.2) still pins 0.7.3, and the newest vinext (1.4.6) still carries the same chain — so no upgrade path existed. Fix: the targeted override `"satori": { "fflate": "0.7.5" }` moves only satori's copy to the patched 0.7.5; `@vitest/ui`'s dev-only fflate 0.8.3 (not in the vulnerable range) is untouched. The other prod copy, `@shuding/opentype.js`'s nested fflate, was already 0.7.5.
- **picomatch** [GHSA-fc5q-39xc-vjpf](https://github.com/advisories/GHSA-fc5q-39xc-vjpf) — listed when this work package was opened, but the advisory was withdrawn upstream ("not a security issue") before any fix was needed; npm's audit database no longer returns it. The production-tree copy (picomatch 2.3.2 under `vinext` → `vite-plugin-commonjs` → `fast-glob` → `micromatch`) needed and got no change.

No advisory without a patched version was left open, so nothing had to be recorded here as unfixable. The audit step, its command and its `--audit-level=high` threshold are unchanged.

**Known, deliberately untouched: dev-tree-only advisories.** After the fix, `npm install` still prints a nonzero summary (e.g. "21 vulnerabilities" counting dependent chains) for advisories in dev-only packages, which `--omit=dev` excludes and which the CI check therefore does not see. They are: vitest / @vitest/mocker (fixed in vitest 4.1.12, we pin ^4.1.6), minimatch 10.2.6 under typescript-estree (fixed in 11.0.1), basic-ftp 5.3.1 under @lhci/cli's get-uri (fixed in 6.2.4+), and lodash-es 4.17.23 pinned by chevrotain under lighthouse (4.18.1 is patched). All run only on developer machines and CI, never in production. Fixing them means dev-dependency upgrades with no effect on the audit gate; that churn is left for a dedicated work package, not smuggled into this one.
