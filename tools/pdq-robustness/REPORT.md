# PDQ robustness report: how well our matching catches altered copies

Generated by `npm run report` in tools/pdq-robustness on 2026-11-19 (crawler v2 WP36). The hashes are the production pipeline's own: `crawler/src/prepare.ts` (the crawler's decode recipe and sharp) plus `asmita/src/lib/pdq/pdq.ts`, imported, not copied. The pool side of every distance is the ORIGINAL image's hash (what a survivor submitted); the query side is the ALTERED copy (what a site serves). Match threshold in production: `PDQ_MATCH_THRESHOLD` = 31; this work package does not change it.

**The test set is harmless by construction**: synthetic images generated in code (gradients, vector shapes, pseudo-text glyphs, value-noise textures, a procedural landscape) plus curated public-domain landscape photographs fetched at run time from Wikimedia Commons with their licence recorded below. No photos of people, nothing intimate, no real-case data. Nothing generated is committed: images live only in `out/` (gitignored) and are rebuilt at run time.

Test set: 21 originals (15 synthetic in five classes, three container formats; 6 public-domain photographs), 800x600. Of those, 18 pass the quality floor and each is altered 30 ways plus 4 realistic stacks — 612 altered copies, 633 images hashed in all. Production rules applied in the "caught (production)" view: a copy below PDQ quality 50 would be skipped by the crawler (`MIN_QUALITY`) whatever its distance, so it is never caught in production.

Conventions: pixel alterations are encoded losslessly (PNG) so each row measures its alteration alone; the `jpeg-quality` rows are the only pure recompressions; `stacked` rows combine an alteration with a re-upload recompression. Crops are centre crops (the percentage is removed from both width and height, split evenly). Rotations fill the exposed corners black. The alteration matrix runs only on originals that pass the quality floor themselves — production can never catch a copy of an image whose hash falls below it — while excluded originals stay in the set for false-match pressure.

Caught at t = Hamming distance(original, copy) <= t. Thresholds: 20, 25, 31, 40 — 31 is the production threshold. Threshold 40 is outside production range (the pool threshold is capped at 31) and is shown only to see how distances behave beyond it.

## Reference agreement: our PDQ vs Thorn's perception (Meta's PDQ via pdqhash)

**Not measured in this run.** To add the reference: set up the Python environment (see README), run `python/perception_ref.py`, then re-run `npm run report`. The reference hashes the same files in `out/images` with `perception.hashers.PDQHash` (Apache-2.0), which wraps Meta's C++ PDQ through the `pdqhash` bindings, decoded by OpenCV.

## Recommendation

**Keep the production threshold at 31.** This run measured it, not assumed it:

- False matches: 0 of 210 unrelated pairs fall within 31 (0 of them between images that both pass the quality floor). The closest unrelated pair sits at 106 bits — a clear margin above the threshold.
- Recall: the common re-upload alterations (recompression, modest resize, mild brightness/contrast, screenshot resampling, slight blur, small crops) are caught at 31: 88% pooled. Tightening to 25 would drop that to 88% and strand 2% of all copies that sit between 25 and 31; loosening to 40 would recover only 4% of all copies (those between 31 and 40).

**What PDQ misses at 31, for the SSCD second layer** (pooled catch at 31, worst first):

- border: 0% caught (mean distance 93.5, max 138) — geometry changes move the DCT grid, which PDQ cannot absorb.
- mirror: 0% caught (mean distance 128.1, max 134) — a mirrored copy is a different picture to PDQ; we ship no dihedral variants.
- rotate: 0% caught (mean distance 88.3, max 150) — geometry changes move the DCT grid, which PDQ cannot absorb.
- crop: 1% caught (mean distance 94.3, max 142) — geometry changes move the DCT grid, which PDQ cannot absorb.
- sticker: 75% caught (mean distance 25.7, max 76) — geometry changes move the DCT grid, which PDQ cannot absorb.
- Partly caught (>= 90% but not all): resize (99%).

These misses are PDQ's known geometry weakness, not a threshold problem: the distances are far beyond any usable threshold. The second-layer matcher that the SSCD work package adds should cover exactly the transformations listed above — mirror, rotation, large crops, and heavy overlays — before any thought of changing the threshold.

## Caveats

- The originals are 800x600. A different base size shifts a few distances (the PDQ 512x512 downsample interacts with image size), but the pattern holds: this was spot-checked by the resize rows.
- Synthetic classes (flat gradients especially) hash at low PDQ quality and behave worse than photographs; the per-class table separates that. Real photographs behave like the `pd-landscape` class.
- The set is small (21 originals) and synthetic-plus-PD-photos, not a real-case corpus; absolute percentages are indicative, the ordering of alterations is the signal.
- The survivor's fingerprint is the ORIGINAL here; a survivor may submit a fingerprint of an already-altered copy, which shifts distances slightly in her favour (the copy on the site is then closer to what she signed).
- The perception reference shares the same test set but decodes with OpenCV; its numbers measure the algorithm, ours measure algorithm + our decoder, which is what production runs.
